### アクティベーションは独立したステップとして実行する {#run-the-activation-as-its-own-step}

CLIは、`$GITHUB_ENV`を通じて設定を公開します。GitHub Actions は、この設定をジョブの<strong>後続の</strong>ステップに適用します。Build Cacheのアクティベーションとビルドの実行を同じ`run:`ブロック内で行うと、ビルドは設定を認識しません。

アクティベーションは、ビルドを実行するステップより前の独立したステップで行ってください。

### フォークからトリガーされた Workflows では Build Cache を使用できません {#workflows-triggered-by-forks-cannot-use-the-build-cache}

ワークフローの実行がフォークからトリガーされた場合、GitHub は実行にシークレットや OIDC トークンへのアクセスを許可しません。そのため、CLI はこれらの実行で認証できず、アクティベーションのステップが失敗します。フォークからの実行では、アクティベーションのステップをスキップしてください。たとえば、`github.event.pull_request.head.repo.full_name` コンテキストを使用して、実行がフォークからのものかどうかを確認できます。

```yaml
- name: Activate Bitrise Build Cache for Gradle
  if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
  run: /tmp/bin/bitrise-build-cache activate gradle --cache --cache-push
```

### 依存関係のキャッシュとBuild Cacheを分けて考える {#keep-dependency-caching-separate-from-the-build-cache}

`actions/cache`は<strong>依存関係のキャッシュ</strong>を行います。GradleやCocoaPodsのキャッシュなど、ビルドがダウンロードするパッケージを保存し、次回の実行時に復元することで、再度取得する必要をなくします。Bitrise CIでは、キーベースのキャッシュStepsが同じ役割を果たします。詳細については、[Dependencies and caching overview](/bitrise-ci/dependencies-and-caching/dependencies-and-caching-overview)を参照してください。

これは、ビルド自体の<strong>出力</strong>（コンパイル済みクラス、コンパイル済みソース、タスクの結果）を再利用するBitrise Build Cacheとは別の役割です。この2つは組み合わせて効果を発揮するため、引き続き依存関係をキャッシュしてください。

やってはいけないのは、ビルドの出力をdependency cacheに含めることです。たとえば、`actions/cache`がGradleのローカルのbuild cacheディレクトリ（`~/.gradle/caches/build-cache-1`）を復元すると、復元されたローカルコピーが、Bitrise Build Cacheが提供するはずの結果を返してしまい、リモートキャッシュのヒット率がほぼゼロまで低下します。キャッシュするのは依存関係のディレクトリであり、ビルド出力のディレクトリではありません。
