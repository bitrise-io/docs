:::warning[Docker Hub のレート制限]

2024年7月15日から、Docker Hub からのダウンロードにレート制限が適用されます。認証なしでBitriseビルド中に弊社のLinuxマシン上でDocker Hub からDockerイメージをプルすると、レート制限の影響で問題が発生する可能性があります。

Bitriseは人気の高いパブリックな Docker イメージの一部をミラーリングしていますが、レート制限によるこうした問題を回避するには、次のいずれかの方法があります。

- Docker Hub に対するDockerイメージのプルリクエストを認証します。詳細とDockerの完全なポリシーについては、[Docker Hub のレート制限](https://docs.docker.com/docker-hub/download-rate-limit/)を参照してください。
- イメージの保存先を別のDockerレジストリに切り替えます。

:::

Linux <GlossTerm baseform="stack">stack</GlossTerm>ビルドをローカルで実行できるようにするには、[docker](https://www.docker.com/)が必要です。

- Linuxの場合は、[公式のインストール手順](https://docs.docker.com/engine/installation/linux/)に従ってください。
- Macの場合は、Docker for Macを使うのが最も簡単に始める方法です。

このガイドでは、[このBitrise Androidサンプルプロジェクト](https://github.com/bitrise-samples/sample-apps-android-sdk22)を使用します。

:::caution[イメージサイズが大きいので注意]

公式のBitrise Dockerイメージは、多種多様なツールがプリインストールされているため、サイズがかなり大きくなっています。少なくとも20〜25GBの空きディスク容量が必要です。

:::

[Bitrise CLI](https://www.bitrise.io/cli)に慣れていない場合は、まずそちらを試すことをおすすめします。CLIを完全にマスターする必要はなく、`bitrise local run WORKFLOW`が何を行うかを理解していれば、このチュートリアルには十分です。


## Dockerイメージのダウンロード

1. [docker](https://www.docker.com/)をインストールします。
1. リポジトリに`bitrise.yml`があることを確認します。

   コミットする必要はありませんが、このファイルはリポジトリのルートディレクトリに存在している必要があります。
1. Mac/Linux上のリポジトリのディレクトリに`cd`します。
1. レジストリからイメージをプルします。

   ```bash
   docker pull bitriseio/android-20.04:latest
   ```
1. 次のコマンドを実行します。

   ```bash
   docker run --privileged --env CI=false --volume "$(pwd):/bitrise/src" --volume "/var/run/docker.sock:/var/run/docker.sock" --rm bitriseio/android-20.04:latest bitrise local run WORKFLOW
   ```

   コンテナ内に直接入って試したい場合は、`--rm bitriseio/android-20.04:latest bitrise local run WORKFLOW`を`-it bitriseio/android-20.04:latest bash`に置き換えることで、コンテナ内でインタラクティブなbashシェルを起動できます。例:

   ```bash
   docker run --privileged --env CI=false --volume "$(pwd):/bitrise/src" --volume "/var/run/docker.sock:/var/run/docker.sock" -it bitriseio/android-20.04:latest bash
   ```

   一般的に、プロジェクトがAndroidプロジェクトでAndroid NDKを使用しない場合は、貴重なディスク容量を節約するために[bitriseio/android](https://quay.io/repository/bitriseio/android) Dockerイメージを使用することをおすすめします。他の公式Bitrise Dockerイメージは、[Quayページ](https://quay.io/organization/bitriseio)で確認できます。この例では、`bitriseio/android`のものを使用しています。
1. [Quay](https://quay.io/organization/bitriseio)からDockerイメージをダウンロードします。

   ```bash
   docker pull bitriseio/android-20.04:latest
   ```

   このイメージは10GBを超えるため、ダウンロードにはかなり時間がかかることに注意してください。ダウンロードが失敗したりハングしたりした場合は、同じコマンドを再度実行することでいつでも再開できます。
1. Bitriseのビルド設定(`bitrise.yml`)をリポジトリのルートディレクトリにダウンロードします。

   [bitrise.io](https://www.bitrise.io)上の<GlossTerm baseform="workflow editor">Workflow Editor</GlossTerm>の<strong><GlossTerm baseform="bitrise.yml">bitrise.yml</GlossTerm></strong>タブから、プロジェクトの`bitrise.yml`を[ダウンロード](/bitrise-ci/configure-builds/configuration-yaml/accessing-a-build-s-bitrise-yml-file)できます。
1. ターミナル/コマンドラインで、リポジトリのルートディレクトリに移動します(`cd`)。この場所に`bitrise.yml`があるかを確認してください。

問題を再現しようとする場合は、リポジトリを新しいディレクトリに`git clone`してください。そうすることで、そのディレクトリにはリポジトリにコミットされているファイルのみが含まれるようになります。通常の作業ディレクトリでコマンドを実行しようとすると、再現性に関する問題がよく発生します。作業ディレクトリには、たとえば`.gitignore`内のファイルなど、リポジトリにコミットされていないファイルが含まれている可能性が高いためです。


## ビルドの実行

次のコマンドでビルドを実行します。

```bash
docker run --privileged --env CI=false --volume "$(pwd):/bitrise/src" --volume "/var/run/docker.sock:/var/run/docker.sock" --rm bitriseio/android:latest bitrise local run WORKFLOW
```

- `--rm bitriseio/android:latest bitrise local run WORKFLOW`

  `-it bitriseio/android:latest bash`を指定すると、コンテナ内でインタラクティブなbashシェルを起動できます。

  例:

  ```bash
  docker run --privileged --env CI=false --volume "$(pwd):/bitrise/src" --volume "/var/run/docker.sock:/var/run/docker.sock" -it bitriseio/android:latest bash
  ```

  このコマンドは、現在のディレクトリ(リポジトリのディレクトリ)をDockerコンテナと共有ボリュームとして共有し、コンテナ内のパス`/bitrise/src`からアクセスできるようにします。

  この後、`bitrise local run WORKFLOW`を実行すると、コンテナ内でWorkflowが実行されます。コンテナから抜けるには、`exit`を実行するだけです。
- `bitrise.yml`内の`WORKFLOW`は、`primary`のような実際のWorkflow IDに置き換えるのを忘れないでください。

- `--env CI=false`フラグは環境変数`CI`を`false`に設定します。これにより、CI環境でのみ意味のある特定のStepをBitrise CLIがスキップするようになります。たとえば、`Git Clone` <GlossTerm baseform="step">Step</GlossTerm>の場合、コードはすでに手元にあるため、Dockerコンテナ内で再度git cloneする必要はありません(そのためコードのディレクトリを`--volume`として共有しました)。
- `--rm`フラグは、`docker run`コマンドの終了後にコンテナを破棄するようDockerに指示します。つまり、コマンドを再度実行しても、`docker run ..`コマンドの実行間で保持されるのは、共有された`--volume`(リポジトリのディレクトリ内)に保存されているファイルのみです。それ以外の、一時的な場所などに生成されるファイルはすべて破棄され、保持されません。

  ビルドが失敗した後にコンテナをデバッグしたい場合は、`--rm`フラグを自由に削除し、既存のDockerコンテナに接続する方法について解説したDockerチュートリアルを確認してください。同じコマンドを再度実行しても、同じコンテナは使用されず、新しいコンテナが作成される点に注意してください。
- `--privileged`フラグは、Dockerコンテナからホストへのアクセス制御を許可します。そのため、使用するDockerイメージを信頼できる場合を除き、このフラグは絶対に使用しないでください!このフラグは、たとえばVPNを機能させる(ホストのネットワーク設定を変更する)ために必要です。
- `--volume "/var/run/docker.sock:/var/run/docker.sock"`フラグは、ホストのDockerソケットをコンテナに公開します。これは、コンテナ内から他のDockerコンテナを実行したい場合や、ビルド中/コンテナ内で`docker`コマンドを実行したい場合に必要です。
