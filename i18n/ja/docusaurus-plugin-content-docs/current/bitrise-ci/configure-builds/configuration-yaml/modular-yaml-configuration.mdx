:::important[Enterpriseプラン限定]

モジュール化されたYAML設定は、<GlossTerm baseform="workspace">Workspaces</GlossTerm>のEnterpriseプランでのみご利用いただけます。また、bitrise.io上にではなく、[設定ファイルを自分のリポジトリに保存する](/bitrise-ci/configure-builds/configuration-yaml/storing-an-apps-configuration-yaml#storing-the-bitriseyml-file-in-your-repository)必要があります。

もしEnterpriseプランをご利用でなくても、モジュール化されたYAMLにご関心がある場合は、[お問い合わせください](http://www.bitrise.io/contact)。

:::

モジュール化されたYAML設定を使うと、大規模で複雑なYAMLファイルを、より小さなモジュール単位のコンポーネントに分割できます。これにより、複数のリポジトリ間での再利用が容易になります。YAMLファイルをモジュール化することで、設定をすばやく見つけて更新できるようになり、エラーやマージコンフリクトのリスクを減らせます。

モジュール化されたYAML設定には、次の要素が含まれます。

- リポジトリのルートにある`bitrise.yml`ファイル。
- 同じリポジトリまたは別のリポジトリにある、その他のYAMLファイル。別のリポジトリからファイルをインクルードするには、そのリポジトリがメインのリポジトリと同じGitアカウントまたはOrganizationに属している必要があります。
- `bitrise.yml`ファイル内の1つ以上の`include`キーワード。これらは他のYAMLファイルを指し示し、それらの設定をメインのプロジェクト設定に取り込みます。

追加のYAMLファイルが`bitrise.yml`ファイルにインクルードされた後は、他のWorkflowやPipelineと同様に、そのファイル内の<GlossTerm baseform="workflow">Workflows</GlossTerm>や<GlossTerm baseform="pipeline">Pipelines</GlossTerm>を設定内で参照できます。


## 複数のYAMLファイルから設定をインクルードする

モジュール化された設定を作成するには、次の作業が必要です。

1. リポジトリに`bitrise.yml`ファイルを保存します。
1. `bitrise.yml`に加えて、さらにYAMLファイルを作成し、リポジトリにコミットします。これらのファイルを設定モジュールと呼びます。

:::important[ファイル数の上限]

ルートレベルの`bitrise.yml`ファイルを含めて、設定ファイルは合計で50個まで作成できます。

:::

`bitrise.yml`では、`include`キーワードを使ってYAML設定モジュールをインクルードできます。モジュールが`bitrise.yml`ファイルと同じリポジトリにある場合、`include`キーワードにはモジュールの場所を示す`path`という1つのパラメーターが必要です。

指定するパスは、リポジトリのルートからの相対パスである必要があります。

```yaml
include:
  - path: file/path/common.yml
```

別のリポジトリにあるYAML設定モジュールをインクルードするには、そのファイルを含むリポジトリを指定します。`repository`プロパティに加えて、次のうち少なくとも1つを設定する必要があります。

- `branch`: YAML設定モジュールを含むブランチ。
- `commit`: YAML設定モジュールをインクルードする際の特定のコミットハッシュ。
- `tag`: YAML設定モジュールを指すGitタグ。

リポジトリは、プロジェクトのメインリポジトリと同じGitアカウントまたはOrganizationに属している必要があります。bitrise.io上で[BitriseprojectのリポジトリURL](/bitrise-platform/projects/configuring-the-repository-url-and-the-default-branch#changing-the-repository-url)を確認できます。たとえば、リポジトリのURLがgit@github.com:MyOrg/main_repo.gitの場合、GitHub上でMyOrgに属するリポジトリのみを参照できます。

リポジトリの名前だけを指定すれば十分です。たとえば、git@github.com:MyOrg/another_repo.gitは`another_repo`という値で参照できます。

```yaml
include:
  - path: shared/common.yml
    branch: test_branch
    repository: another_repo
```

:::important[他のリポジトリへのアクセス]

Bitriseが<GlossTerm baseform="configuration yaml">設定YAML</GlossTerm>ファイルをホストしているall repositoriesにアクセスするには、`read`アクセス権が必要です。Bitriseがリポジトリにアクセスできるようにする方法は2つあります。

- [GitHub App](/bitrise-platform/repository-access/github-app-integration)インテグレーションを使用している場合は、プロジェクトに[追加のリポジトリをリンクできます](/bitrise-platform/repository-access/github-app-integration#additional-linked-repositories-via-a-github-app)。
- その他の認証方法については、次のガイドを参照してください。[サブモジュールまたはプライベートリポジトリの依存関係を持つApp](/bitrise-platform/repository-access/apps-with-submodules-or-private-repo-dependencies)

:::


## `include`のフォーマット

| パラメーター | 必須か | 説明 |
| --- | --- | --- |
| `path` | 必須 | インクルードするYAMLファイルの場所。パスは次のいずれかからの相対パスです。  - CI環境ではリポジトリのルート。 - ローカル環境では現在のディレクトリ。 |
| `branch` | 任意 | YAMLファイルをインクルードするブランチ。 |
| `tag` | 任意 | YAMLファイルをインクルードするタグ。`branch`と`tag`の両方が指定されている場合は、タグが優先されます。 |
| `commit` | 任意 | YAMLファイルをインクルードする特定のコミットハッシュ。 `branch`、`tag`、`commit`のすべてが指定されている場合は、コミットが優先されます。 |
| `repository` | 任意 | YAMLファイルの取得元となるリポジトリ。URLではなく、リポジトリの名前を設定するだけで構いません。 |


## 設定モジュールを定義する

設定モジュールは、完全なYAML設定ファイルです。つまり、有効な`bitrise.yml`ファイルのすべての設定要素を利用できるということです。設定モジュールでは、`format_version`、アプリレベルのEnvironment Variables、デフォルトのstack<GlossTerm baseform="stack"></GlossTerm>やマシンタイプ、そしてもちろんPipelines、Stage、Workflowsを定義できます。

たとえば、単に別のモジュールを指すだけの、最小限の`bitrise.yml`ファイルを作成できます。

```yaml
include:
  - path: path/to/config_module.yml
```

この場合、`config_module.yml`にはビルドの設定がすべて含まれます。

```yaml
format_version: 13
default_step_lib_source: https://github.com/bitrise-io/bitrise-steplib.git
project_type: android
app:
  envs:
  - MY_NAME: My Name
workflows:
  test:
    steps:
    - script:
        inputs:
        - content: echo "Hello ${MY_NAME}!"
```

設定モジュールには、ルートレベルで定義されるあらゆる設定エンティティを含めることができます。たとえば、単一のWorkflowのみ、またはアプリレベルのEnvironment Variablesのみを定義する設定モジュールも問題なく有効です。

`bitrise.yml`ファイル:

```yaml
format_version: 13
default_step_lib_source: https://github.com/bitrise-io/bitrise-steplib.git
include:
  - path: path/to/config_module.yml
```

`config_module.yml`ファイル:

```yaml
app:
  envs:
  - USER_NAME: UserName
workflows:
  test:
    steps:
    - script:
        inputs:
        - content: echo "Hello ${USERNAME}!"
```

ただし、ルートレベル以外のエンティティも、それだけを別のモジュールファイルに単独で置くことはできません。たとえば、<GlossTerm baseform="step">Step</GlossTerm>の入力だけをこのようにインクルードすることはできません。

### インクルードしたモジュールのネスト

インクルードした設定ファイル内で`include`プロパティを使用できます。

ルートレベルの`bitrise.yml`ファイル:

```yaml
format_version: 13
default_step_lib_source: https://github.com/bitrise-io/bitrise-steplib.git
include:
  - path: path/to/config_module.yml
```

`config_module.yml`ファイル:

```yaml
include:
  - path: path/to/another_module.yml
```

`another_module.yml`ファイル:

```yaml
workflows:
  ui_test:
    steps:
    - pull-intermediate-files@1:
        inputs:
        - artifact_sources: build_tests.build_for_ui_testing
```

この設定により、`ui_test`のWorkflowを実行できるようになります。

ネストには次の制限があります。

- ルートレベルのファイルを含めて、深さは10までです。
- ルートレベルのファイルを含めて、設定ファイルは合計50個までです。

### インクルードしたモジュールのマージルール

Bitriseがビルドを実行する際、設定モジュールは1つの`bitrise.yml`ファイルにマージされます。

- インクルードされたモジュールは、ルートの`bitrise.yml`ファイルで定義された順序で読み込まれ、設定にマージされます。
- インクルードされたモジュールがさらにincludeを使用している場合、ネストされたモジュールが先に再帰的にマージされます。
- includeで追加されたすべての設定ファイルがマージされた後、その結果の設定はルートレベルの`bitrise.yml`ファイルとマージされます。そのため、ルートレベルで設定値を上書きできます。

:::note[bitrise.ioへの切り替えに戻す]

複数のYAMLファイルを使ったモジュール化された設定がある状態で、[設定の保存先をbitrise.ioに戻す](/bitrise-ci/configure-builds/configuration-yaml/storing-an-apps-configuration-yaml#moving-the-bitriseyml-file-back-to-bitriseio)と、同じマージルールを使ってすべてのファイルが1つの`bitrise.yml`ファイルにマージされます。

:::

設定をマージする際には、値が重複してインクルードされた設定値が上書きされることがあります。YAMLモジュールをマージする場合、最後に読み込まれたファイルが、既存のマージ済み設定よりも優先されます。ルールは次のとおりです。

- 単純な型の項目(整数やブール値など): 最後に読み込まれたファイルの値が使用されます。
- オブジェクト型の項目(Pipelines、Stage、Workflowsなど):

  - プロパティが既存のマージ済み設定にのみ存在する場合、その値が保持されます。
  - プロパティが両方に存在し、その値がハッシュマップである場合、値がマージされます。
  - それ以外の場合は、最後に読み込まれたファイルの値が使用されます。
- 配列型の項目(Environment Variablesのリストや[トリガーマップの項目](/bitrise-ci/run-and-analyze-builds/build-triggers/yaml-syntax-for-build-triggers)など): このコレクションが最後に読み込まれたファイルと既存のマージ済み設定の両方に存在する場合、マージ後の値は順序付きの配列となり、既存のマージ済み設定のすべての値の後に、最後に読み込まれたファイルの値が続きます。

マージされた設定は、<strong>Merged config</strong>タブの<GlossTerm baseform="workflow editor">Workflow Editor</GlossTerm>で確認できます。そこから個々のモジュールを開いて編集する方法については、[Workflow Editorでモジュール化された設定を編集する](/bitrise-ci/configure-builds/configuration-yaml/editing-a-modular-configuration-in-the-workflow-editor)を参照してください。

<strong>マージルール</strong>

`config_module.yml`ファイルをインクルードするルートの`bitrise.yml`ファイルがあるとします。

`bitrise.yml`:

```yaml
format_version: 13
default_step_lib_source: https://github.com/bitrise-io/bitrise-steplib.git
project_type: android

include: 
  - path: path/to/config_module.yml

app:
  envs:
  - USER_ID: UserId
  - PASSWORD: SecurePassphrase
```

`config_module.yml`:

```yaml
format_version: 10

app:
  envs:
  - USERNAME: UserName

workflows:
  test:
    steps:
    - script:
        inputs:
        - content: echo "Hello ${USERNAME}!"
```

マージ中に、`config_module.yml`が読み込まれ、設定にマージされます。次に、ルートレベルの`bitrise.yml`が読み込まれ、マージされます。最終的な設定は次のようになります。

```yaml
format_version: 13
default_step_lib_source: https://github.com/bitrise-io/bitrise-steplib.git
project_type: android

app:
  envs:
  - USER_ID: UserId
  - PASSWORD: SecurePassphrase
  - USERNAME: UserName

workflows:
  test:
    steps:
    - script:
        inputs:
        - content: echo "Hello ${USERNAME}!"
```

- ルートレベルの`format_version`プロパティは両方のファイルに存在します。ルートレベルの`bitrise.yml`ファイルは全体の設定に最後にマージされるため、その`format_version`の値が使用されます。
- `apps`プロパティは両方のファイルに存在するため、すべてのキーと値のペアが全体の設定に追加されます。
- `test`のWorkflowは`config_module.yml`にのみ存在するため、全体の設定に追加され、`bitrise.yml`によって上書きされることはありません。
