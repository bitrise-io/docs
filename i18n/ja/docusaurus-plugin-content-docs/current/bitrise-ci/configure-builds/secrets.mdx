<GlossTerm baseform="secret">Secrets</GlossTerm> は環境変数の一種で、情報を暗号化された形式で隠し、その値はビルドログに表示されません。`bitrise.yml` の設定にも表示されません。パスワードや API キーなどの機密情報を Secrets として保存できます。

Environment Variables と同様に、Secrets は <GlossTerm baseform="step">Step</GlossTerm> 入力の値として使用できます：[Env Var を Step 入力として使用する](/bitrise-ci/configure-builds/environment-variables#using-an-env-var-in-a-step-input)。

Secrets の管理方法は2つあります。

- プロジェクトレベル：Secret は1つのプロジェクトに属します。
- Workspace レベル：Secret は複数のプロジェクトで共有されます。詳細は、[複数のプロジェクトにまたがる Secrets の管理](#managing-secrets-across-multiple-apps)を参照してください。

プロジェクトの <strong>Secrets</strong> ページには、その両方が一覧表示されます。共有 Secrets がある場合は最初に、続いて project level Secrets が表示されます。特に記載がない限り、このページの手順は project level Secrets を対象としています。


## Secretの設定 {#setting-a-secret}

:::note[すべての環境変数の値は文字列です]

環境変数またはシークレットの値には文字列のみを設定できます。数値（例：7）を設定した場合でも、文字列として渡されます。

:::

シークレットは、<GlossTerm baseform="workflow editor">Workflow Editor</GlossTerm>の<strong>Secrets</strong>ページで作成するか、Step inputsを変更する際に作成できます。

<strong>Secrets</strong>タブで新しいシークレット環境変数を追加したら、いつでもそこに戻って内容を変更したり、詮索好きな目から保護したりできます。

## Secretの値の保護 {#protecting-the-value-of-a-secret}

通常、<strong>目</strong>のアイコンをクリックすると、Secret の値を<strong>表示</strong>または<strong>非表示</strong>にできます。この機能は、<strong>Secrets</strong> にシークレット環境変数が多数ある場合に、1つの Secret の値だけを確認し、他の値は非表示のままにしたいときに便利です。値が非表示の場合は、<strong>斜線付きの目</strong>のアイコンで表されます。

ただし、Secret を保護対象にすると、値全体を完全に非表示にできます。保護対象にすると、自分自身を含め誰も値全体を再び表示できなくなりますが、新しい値に置き換えることはできます。値の長さが16文字を超える場合は、最後の4文字を表示できます：[保護された Secrets のマスク表示](#masked-review-of-protected-secrets)。

:::warning[Secret の保護は元に戻せません]

Secret を保護対象にすると元に戻せません。保護を再びオフにすることはできません。保護された Secret の値は、<strong>Edit</strong> をクリックして新しい値を入力すれば置き換えられます。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で <strong>Secrets</strong> を選択します。
1. Secret の値の横にある <strong>Edit</strong> をクリックします。

   ![edit-button-secrets.png](/img/_paligo/uuid-2de8b6b8-3fc0-5da9-9f45-1b22546e1bb2.png)
1. <strong>Protected</strong> にチェックを入れます。
1. この操作は元に戻せないという警告がダイアログに表示されます。<strong>Save and protect</strong> をクリックします。

以上で完了です。これ以降、Secret の値全体を表示することはできません。

### 保護された Secrets のマスク表示 {#masked-review-of-protected-secrets}

保護された Secret の値の長さが16文字を超える場合は、最後の4文字を表示できます。値の長さが16文字以下の場合は、値のどの部分も表示できません。

1. Secret を探します。

   Project level Secrets は、プロジェクトの <strong>Secrets</strong> ページにあります。共有 Secrets は、<strong>Workspace settings</strong> の <strong>Shared resources</strong> ページにあります。
1. Secret の値の横にある小さな<strong>目</strong>のアイコンをクリックします。

   Secret が保護されている場合、値の長さが16文字を超えていれば、値の最後の4文字が表示されます。保護された Secret の値がそれより短い場合は、アスタリスクと値の合計の長さのみが表示されます。

   ![Masked value of a protected Secret in the Secrets tab, showing the last four characters and the total length](/img/configure-builds/2026-11-17-masked-review-protected-secret.png)


## Secretのプルリクエストへの公開 {#exposing-a-secret-to-pull-requests}

デフォルトでは、プルリクエストはSecretsの値にアクセスできません。つまり、リポジトリのフォークから作成されたプルリクエストがビルドを<GlossTerm baseform="trigger">トリガー</GlossTerm>する場合、そのビルドではプロジェクトのSecretsを使用できません。

特定のSecretへのアクセスをプルリクエストビルドに許可する必要がある場合は、そのSecretをプルリクエストに公開できます。ただし、公開した場合でも、その値はログには表示されず、[REDACTED]と表示されます。

:::important[保護されたSecretsは公開できません]

Secretが[保護対象に設定される](/bitrise-ci/configure-builds/secrets#protecting-the-value-of-a-secret)と、プルリクエストビルドに公開することはできません。

:::

:::important[公開プロジェクト]

プロジェクトが公開プロジェクトの場合、そのプロジェクトのSecretsをプルリクエストビルドに公開することはできません。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. Secretの値の隣にある<strong>Edit</strong>をクリックします。
1. <strong>Expose for Pull Requests?</strong>トグルを切り替えます。

Secretが公開されると、プルリクエストビルドからアクセスできるようになります。


## 複数のプロジェクトにまたがるSecretsの管理 {#managing-secrets-across-multiple-apps}

デフォルトでは、すべてのSecretsはプロジェクトレベルで管理されます。各プロジェクトで対応する値が異なっていても、複数のプロジェクト間でSecretのキーを再利用できます。

ただし、すべてのプロジェクトで同じ値を保持するSecretを設定し、そのSecretを1か所で管理することも可能です。例えば、すべてのプロジェクトが同じAPIへのアクセスを必要とする場合は、APIキーを含むSecretを一元的な場所に保存するのが適切です。APIキーが変更された場合も、その1か所で変更するだけで、すべてのプロジェクトに反映されます。

これを実現する方法は2つあります。

- [WorkspaceからSecretsを管理する](#managing-secrets-on-a-workspace-level)。これはEnterpriseプランでのみ利用できます。
- vaultやデータベースなどの[一元的な場所からSecretsを管理](#managing-secrets-from-a-central-vault-or-database)し、Stepを使用して取得する。

### Workspace レベルでの Secrets の管理 {#managing-secrets-on-a-workspace-level}

Enterprise プランでは、Secrets を Workspace レベルで保存できます。つまり、同じ Secret を、その Workspace が所有するすべてのプロジェクトで利用できます。これによりセキュリティが向上します。Workspace のオーナーとマネージャーだけが、これらの Secrets にアクセスできます。

:::note[Downgrading]

Enterprise プランからダウングレードすると、Workspace Secrets は project level Secrets に変換されます。

:::

ビルドに Secrets を渡す際は、[利用可能性の順序](/bitrise-ci/configure-builds/environment-variables#availability-order-of-environment-variables)に従い、project level Secrets が Workspace レベルの Secrets より優先されます。つまり、同じキーを持つ Secrets が2つある場合、ビルドではプロジェクトレベルの Secret が使用されます。

新しい Secret を追加するには：

1. Bitrise のメインページで、左側のナビゲーションメニューから <strong>Settings</strong> を選択します。<strong>Workspace settings</strong> ページが開きます。
1. <strong>Workspace settings</strong> ページで <strong>Shared resources</strong> を選択します。

   ![shared-res.png](/img/_paligo/uuid-8b262205-594a-d6ae-9985-3c47a3df5175.png)
1. <strong>Add new</strong> ボタンをクリックします。
1. キーと値を追加します。

   ![ws-secrets.png](/img/_paligo/uuid-0d1616e8-82d6-9de7-f192-1aab7058880b.png)
1. Secret の使用方法を設定します。

   - <strong>Replace variables in inputs</strong>：Secret の値を文字列としてビルドに渡します。埋め込みの Secrets や Environment Variables に使用します。つまり、Secret の値が別の Secret または環境変数のキーである場合です。ほとんどの場合、チェックを入れる必要はありません。
   - <strong>Expose for pull requests</strong>：Secret を PR に公開すると、その Secret をプルリクエストビルドで使用できるようになります。リポジトリのプライバシー設定によっては、セキュリティ上のリスクになる可能性があります。
   - <strong>Protected</strong>：値全体を表示できなくなり、値が16文字を超える場合に限り、最後の4文字のみ表示できます。値を置き換えることは引き続き可能です。この設定は、保存すると元に戻せません。詳細は、[保護された Secrets のマスク表示](#masked-review-of-protected-secrets)を参照してください。
1. 準備ができたら、<strong>Done</strong> をクリックします。

### 一元的なvaultやデータベースからSecretsを管理する {#managing-secrets-from-a-central-vault-or-database}

一元的な場所にSecretsを設定するには、次の2つが必要です：

- Secretsを保存するための一元的なvaultまたはデータベース（HashiCorpやDopplerなど）。CLI経由でアクセスできる必要があります。
- 一元的なvault/データベースにアクセスし、シークレットを取得してBitrise上で機密として設定するための<strong>Script</strong> Step。

ビルド中に新しいシークレットを作成し、一元的な場所に保存するには：

1. 保存したいvaultまたはデータベースに、Secretsをキーと値のペアとして追加します。
1. Secretsを使用したいすべてのWorkflowsに、<strong>Script</strong> Stepを追加します。
1. vaultにアクセスしてSecretsを取得するために必要なコマンドを追加します。具体的なコマンドは使用しているサービスによって異なります。
1. `envman`ツールを使用して、Secretsを機密としてマークします。envmanツールの構文は次のとおりです。

   `envman add --key KEY --value value --sensitive` .
1. Stepがビルドログにシークレットの値を表示しないようにします。そのためには、Stepの`content`から`set -x`を削除します。

:::warning[シークレットのマスキング]

シークレットのマスキングをオフにしている場合、Secretsはマスキングされず、値がログに表示される可能性があるのでご注意ください。

:::

<strong>SecretsをHashiCorp Vaultに保存する</strong>

`secret/hello`という名前の[HashiCorp Vault](https://www.vaultproject.io/)インスタンスがあるとします。このvaultインスタンスには2つのSecretsがあります。値が`world`の`foo`と、値が`world2`の`foo2`です。これらのSecretsをBitriseビルドで使用するには、次の操作が必要です。

- vaultインスタンスからエクスポートします。
- それらを反復処理し、両方を機密としてマークします。

これらを実現するには、次のScriptを使用できます：

```bash
# Exporting the Secrets
vault kv get --format=json secret/hello | jq -r '.data.data | to_entries[] | [.key, .value] | @tsv' | 
# Iterating over the Secrets and marking them as sensitive
while IFS=$'\t' read -r key value; do
    envman add --key "$key" --value "$value" --sensitive
done
```


## Secretsのマスキング {#redacting-secrets}

Bitrise CLIは、Secret Env Varsを自動的にマスキングし、キーの後に改行を入れて`[REDACTED]`を出力します。これにより、Secret Env Varsはビルドログに表示されません。これは非公開プロジェクトと公開プロジェクトの両方に適用されます。

Secretsをログに表示する必要がある場合は、いつでもこの機能をオフにできます。

:::warning

これはセキュリティ上のリスクとなる可能性があります。Secretのマスキングをオフにしないことを強くおすすめします。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. <strong>Add new</strong>をクリックして、`BITRISE_SECRET_FILTERING`シークレットEnvironment Variableを偽の値で登録します。
1. 右上の<strong>Save changes</strong>をクリックします。


## セルフホスト環境におけるSecrets {#secrets-in-self-hosted-environments}

Bitriseビルドはself-hosted infrastructure（自分で管理するハードウェアまたは仮想化環境）で実行できます。セキュリティポリシー上、bitrise.ioでホストされているBitrise Secretsを使用できない場合、このガイドではSecretsにアクセスしてビルドで使用するための別の方法を紹介します。

セルフホストビルドでは、ホストマシンは仮想プライベートクラウドの内側にあります。そのため、SecretsをBitriseのコントロールプレーンやウェブサイトに公開することなく、任意のシークレットサービスにアクセスできます。使用しているサービスからシークレットを取得し、`envman`を使用してBitriseビルドに追加します：

1. 必要に応じて、Bitriseで任意の値を持つプレースホルダーのシークレットを作成します。[シークレットの設定](/bitrise-ci/configure-builds/secrets#setting-a-secret)を参照してください。

   これは、Workflow EditorのGUI上で機密のStep入力にシークレットを使用したい場合にのみ必要です。機密入力ではSecretsのみを受け付け、Workflow Editorでは既存のSecretsのみを機密入力の値として追加できます。

   YAMLでBitriseの設定を編集する場合は、入力に任意の値を設定できるため、プレースホルダーは不要です。
1. 使用しているサービスからシークレットを取得するために、<strong>Script</strong> Stepを使用します。
1. スクリプト内で、`set +x`を設定してデバッグをオフにします：

   これは非常に重要です。デバッグモードでは、シークレットの値がビルドログに表示される可能性があります。

   ```bash
   #!/usr/bin/env bash
   # fail if any commands fails
   set -e
   # make pipelines' return status equal the last command to exit with a non-zero status, or zero if all commands exit successfully
   set -o pipefail
   # debug log
   set +x
   ```
1. 使用しているサービスからシークレットの値を取得し、`envman`に追加します。

   ```bash
   set +x
   GIT_PASSWORD_SECRET=TODO Your call to fetch the secret value
   envman add --key GIT_HTTP_PASSWORD --value $GIT_PASSWORD_SECRET
   ```

   実際のコマンドは使用しているサービスによって異なります。例えば、AWSでBitriseを使用しており、EC2マシンがAWS Secrets Managerにアクセスできる場合、次のようなコマンドでシークレットを取得できます：

   ```bash
   set +x
   USERNAME=aws secretsmanager get-secret-value --secret-id BitriseDemoGitUsername --region eu-central-1 | jq  -r '.SecretString'
   envman add --key GIT_HTTP_USERNAME --value $USERNAME
   PASS=aws secretsmanager get-secret-value --secret-id BitriseDemoGitPassword --region eu-central-1 | jq  -r '.SecretString'
   envman add --key GIT_HTTP_PASSWORD --value $PASS
   ```
