<GlossTerm baseform="secret">Secrets</GlossTerm>は特定の種類の環境変数で、情報を暗号化された形式で隠し、その値はビルドログに表示されません。また、`bitrise.yml`の設定にも表示されません。パスワードやAPIキーなどの機密情報をSecretsとして保存できます。

Environment Variablesと同様に、Secretsは<GlossTerm baseform="step">Step</GlossTerm>入力の値として使用できます。[環境変数をStep入力として使用する](/bitrise-ci/configure-builds/environment-variables#using-an-env-var-in-a-step-input)


## Secretの設定 {#setting-a-secret}

:::note[すべての環境変数の値は文字列です]

環境変数またはシークレットの値には文字列のみを設定できます。数値(例:7)を設定した場合でも、文字列として渡されます。

:::

シークレットは、<GlossTerm baseform="workflow editor">Workflow Editor</GlossTerm>の<strong>Secrets</strong>ページで作成するか、Step inputsを変更する際に作成できます。

<Tabs>
<TabItem value="secrets-page" label="Secrets page" default>

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. <strong>Project level Secrets</strong>の下にある<strong>Add new</strong>ボタンをクリックします。

   ![secrets-screenshot.png](/img/_paligo/uuid-b269a597-65ef-34a5-1828-ad1ab954437d.png)
1. キーと値を追加します。

   :::important[$記号の使用]

   環境変数やシークレットの値(パスワードなど)には`$`記号を使用できますが、その場合は必ず<strong>Replace variables in inputs</strong>オプションのチェックを外したままにしてください。変数のキーを値に置き換えて入力に使用すると、`$`記号があるため、Bitrise CLIはその値を別の環境変数として扱います。

   :::
1. 必要に応じて、[シークレットのキーを入力内でその値に置き換える](/bitrise-ci/configure-builds/environment-variables#replacing-variables-in-inputs)ことができます。<strong>Replace variables in inputs</strong>オプションをチェックしてください。
1. 必要に応じて、このオプションを選択することで、シークレットをプルリクエストに公開できます。

## 既存のSecretの編集 {#editing-an-existing-secret}

<strong>Secrets</strong>タブで新しいシークレット環境変数を追加したら、いつでもそこに戻って内容を変更したり、詮索好きな目から保護したりできます。

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. シークレットの値の隣にある<strong>Edit</strong>をクリックします。
1. 必要に応じて内容を変更します。
1. <strong>Save</strong>をクリックします。


## Secretの値の保護 {#protecting-the-value-of-a-secret}

通常、<strong>目</strong>のアイコンをクリックすることで、シークレットの値を<strong>表示</strong>または<strong>非表示</strong>にできます。この機能は、<strong>Secrets</strong>に多くのシークレット環境変数がある場合に、1つのシークレットの値だけを確認し、他の値は非表示のままにしたいときに便利です。値が非表示の場合は、<strong>斜線の入った目</strong>のアイコンで示されます。

ただし、シークレットを保護対象にすることで、その値を永久に非表示にできます。そうすると、自分自身を含め、誰もその値を再び変更したり表示したりできなくなります。

:::warning[シークレットの保護は元に戻せません]

シークレットを保護対象にする操作は取り消せません。値を変更する必要が生じた場合は、シークレットを削除して新しく作成する必要があります。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. シークレットの値の隣にある<strong>Edit</strong>をクリックします。

   ![edit-button-secrets.png](/img/_paligo/uuid-2de8b6b8-3fc0-5da9-9f45-1b22546e1bb2.png)
1. <strong>Protected</strong>をチェックします。
1. ダイアログにこの処理が取り消せない旨の警告が表示されます。<strong>Save and protect</strong>をクリックします。

これで完了です。シークレットの値は表示できなくなります。


## Secretのプルリクエストへの公開 {#exposing-a-secret-to-pull-requests}

デフォルトでは、プルリクエストはSecretsの値にアクセスできません。つまり、リポジトリのフォークから作成されたプルリクエストがビルドを<GlossTerm baseform="trigger">トリガー</GlossTerm>する場合、そのビルドはアプリのSecretsを使用できません。

特定のシークレットへのアクセスをプルリクエストビルドに許可する必要がある場合は、そのシークレットをプルリクエストに公開できます。ただし、公開した場合でも、その値はログには表示されず、[REDACTED]と表示されます。

:::important[保護されたSecretsは公開できません]

シークレットが一度[保護対象に設定される](/bitrise-ci/configure-builds/secrets#protecting-the-value-of-a-secret)と、プルリクエストビルドに公開することはできません。

:::

:::important[公開アプリ]

アプリが公開アプリの場合、そのアプリのSecretsをプルリクエストビルドに公開することはできません。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. シークレットの値の隣にある<strong>Edit</strong>をクリックします。
1. <strong>Expose for Pull Requests?</strong>トグルを切り替えます。

シークレットが公開されると、プルリクエストビルドからアクセスできるようになります。


## 複数のアプリにまたがるSecretsの管理 {#managing-secrets-across-multiple-apps}

デフォルトでは、すべてのSecretsはアプリレベルで管理されます。各アプリで対応する値が異なっていても、複数のBitriseアプリ間でシークレットキーを再利用できます。

ただし、すべてのアプリで同じ値を保持するシークレットを設定し、そのシークレットを1か所で管理することも可能です。例えば、すべてのアプリが同じAPIへのアクセスを必要とする場合は、APIキーを含むシークレットを一元的な場所に保存すると効率的です。APIキーが変更された場合でも、その1か所を変更するだけで、すべてのBitriseアプリに変更が反映されます。

これを実現する方法は2つあります。

- [WorkspaceからSecretsを管理する](#managing-secrets-on-a-workspace-level)。これはEnterpriseプランでのみご利用いただけます。
- [一元的な場所からシークレットを管理する](#managing-secrets-from-a-central-vault-or-database)ことです。vaultやデータベースなどを使用し、Stepを使って取得します。

### WorkspaceレベルでSecretsを管理する {#managing-secrets-on-a-workspace-level}

Enterpriseプランでは、WorkspaceレベルでSecretsを保存できます。つまり、同じシークレットがそのWorkspaceが所有するすべてのアプリからアクセス可能になるということです。これによりセキュリティが向上し、WorkspaceのOwnerとManagerのみがこれらのSecretsにアクセスできるようになります。

:::note[ダウングレード]

Enterpriseプランからダウングレードすると、Workspace SecretsはアプリレベルのSecretsに変換されます。

:::

Secretsをビルドに渡す際は、[有効順序](/bitrise-ci/configure-builds/environment-variables#availability-order-of-environment-variables)において、アプリレベルのSecretsがWorkspaceレベルのSecretsより優先されます。これは、同じキーを持つSecretsが2つ存在する場合、ビルド中はアプリレベルのシークレットが使用されることも意味します。

新しいシークレットを追加するには:

1. Bitriseのメインページで、左側のナビゲーションメニューから<strong>Settings</strong>を選択します。<strong>Workspace settings</strong>ページに移動します。
1. <strong>Workspace settings</strong>ページで<strong>Shared resources</strong>を選択します。

   ![shared-res.png](/img/_paligo/uuid-8b262205-594a-d6ae-9985-3c47a3df5175.png)
1. <strong>Add new</strong>ボタンをクリックします。
1. キーと値を追加します。

   ![ws-secrets.png](/img/_paligo/uuid-0d1616e8-82d6-9de7-f192-1aab7058880b.png)
1. シークレットの使用の詳細を設定します:

   - <strong>Replace variables in inputs</strong>: シークレットの値を文字列としてビルドに渡します。埋め込みのSecretsやEnvironment Variables(シークレットの値が別のシークレットまたは環境変数のキーである場合)に使用します。ほとんどのユースケースでは、これをチェックする必要はありません。
   - <strong>Expose for pull requests</strong>: シークレットをPRに公開すると、そのシークレットをプルリクエストビルドで使用できるようになります。リポジトリのプライバシー設定によっては、これがセキュリティリスクとなる可能性があります。
   - <strong>Protected</strong>: 値は二度と変更または表示できなくなります。この設定は保存すると元に戻せません。
1. 準備ができたら、<strong>Done</strong>をクリックします。

### 一元的なvaultやデータベースからSecretsを管理する {#managing-secrets-from-a-central-vault-or-database}

一元的な場所にSecretsを設定するには、次の2つが必要です:

- Secretsを保存するための一元的なvaultまたはデータベース(HashiCorpやDopplerなど)。CLI経由でアクセスできる必要があります。
- 一元的なvault/データベースにアクセスし、シークレットを取得してBitrise上で機密として設定するための<strong>Script</strong> Step。

ビルド中に新しいシークレットを作成し、一元的な場所に保存するには:

1. 保存したいvaultまたはデータベースに、Secretsをキーと値のペアとして追加します。
1. Secretsを使用したいすべてのWorkflowsに、<strong>Script</strong> Stepを追加します。
1. vaultにアクセスしてSecretsを取得するために必要なコマンドを追加します。具体的なコマンドは使用しているサービスによって異なります。
1. `envman`ツールを使用して、Secretsを機密としてマークします。envmanツールの構文は次のとおりです。

   `envman add --key KEY --value value --sensitive` .
1. Stepがビルドログにシークレットの値を表示しないようにします。そのためには、Stepの`content`から`set -x`を削除します。

:::warning[シークレットのマスキング]

シークレットのマスキングをオフにしている場合、Secretsはマスキングされず、値がログに表示される可能性があるのでご注意ください。

:::

<strong>SecretsをHashiCorp Vaultに保存する</strong>

`secret/hello`という名前の[HashiCorp Vault](https://www.vaultproject.io/)インスタンスがあるとします。このvaultインスタンスには2つのSecretsがあります。値が`world`の`foo`と、値が`world2`の`foo2`です。これらのSecretsをBitriseビルドで使用するには、次の操作が必要です。

- vaultインスタンスからエクスポートします。
- それらを反復処理し、両方を機密としてマークします。

これらを実現するには、次のScriptを使用できます:

```bash
# Exporting the Secrets
vault kv get --format=json secret/hello | jq -r '.data.data | to_entries[] | [.key, .value] | @tsv' | 
# Iterating over the Secrets and marking them as sensitive
while IFS=$'\t' read -r key value; do
    envman add --key "$key" --value "$value" --sensitive
done
```


## Secretsのマスキング {#redacting-secrets}

Bitrise CLIは、シークレット環境変数を自動的にマスキングし、キーの後に改行を入れて`[REDACTED]`を出力することで、ビルドログにシークレット環境変数が表示されないようにします。これは非公開アプリと公開アプリの両方に適用されます。

ただし、Secretsをログに表示させる必要がある場合は、いつでもこれをオフにできます。

:::warning

これはセキュリティ上のリスクとなる可能性があります。シークレットのマスキングをオフにしないことを強くおすすめします。

:::

1. <Partial_OpeningTheWorkflowEditor />
1. 左側で<strong>Secrets</strong>を選択します。
1. <strong>Add new</strong>をクリックして、値がfalseの`BITRISE_SECRET_FILTERING`シークレット環境変数を登録します。
1. 右上にある<strong>Save changes</strong>をクリックします。


## セルフホスト環境におけるSecrets {#secrets-in-self-hosted-environments}

Bitriseビルドはself-hosted infrastructure(自分で管理するハードウェアまたは仮想化環境)で実行できます。セキュリティポリシー上、bitrise.ioでホストされているBitrise Secretsを使用できない場合、このガイドではSecretsにアクセスしてビルドで使用するための別の方法を紹介します。

セルフホストビルドでは、ホストマシンは仮想プライベートクラウドの内側にあります。そのため、SecretsをBitriseのコントロールプレーンやウェブサイトに公開することなく、任意のシークレットサービスにアクセスできます。使用しているサービスからシークレットを取得し、`envman`を使用してBitriseビルドに追加します:

1. 必要に応じて、Bitriseで任意の値を持つプレースホルダーのシークレットを作成します。[シークレットの設定](/bitrise-ci/configure-builds/secrets#setting-a-secret)を参照してください。

   これは、Workflow EditorのGUI上で機密のStep入力にシークレットを使用したい場合にのみ必要です。機密入力ではSecretsのみを受け付け、Workflow Editorでは既存のSecretsのみを機密入力の値として追加できます。

   YAMLでBitriseの設定を編集する場合は、入力に任意の値を設定できるため、プレースホルダーは不要です。
1. 使用しているサービスからシークレットを取得するために、<strong>Script</strong> Stepを使用します。
1. スクリプト内で、`set +x`を設定してデバッグをオフにします:

   これは非常に重要です。デバッグモードでは、シークレットの値がビルドログに表示される可能性があります。

   ```bash
   #!/usr/bin/env bash
   # fail if any commands fails
   set -e
   # make pipelines' return status equal the last command to exit with a non-zero status, or zero if all commands exit successfully
   set -o pipefail
   # debug log
   set +x
   ```
1. 使用しているサービスからシークレットの値を取得し、`envman`に追加します。

   ```bash
   set +x
   GIT_PASSWORD_SECRET=TODO Your call to fetch the secret value
   envman add --key GIT_HTTP_PASSWORD --value $GIT_PASSWORD_SECRET
   ```

   実際のコマンドは使用しているサービスによって異なります。例えば、AWSでBitriseを使用しており、EC2マシンがAWS Secrets Managerにアクセスできる場合、次のようなコマンドでシークレットを取得できます:

   ```bash
   set +x
   USERNAME=aws secretsmanager get-secret-value --secret-id BitriseDemoGitUsername --region eu-central-1 | jq  -r '.SecretString'
   envman add --key GIT_HTTP_USERNAME --value $USERNAME
   PASS=aws secretsmanager get-secret-value --secret-id BitriseDemoGitPassword --region eu-central-1 | jq  -r '.SecretString'
   envman add --key GIT_HTTP_PASSWORD --value $PASS
   ```
