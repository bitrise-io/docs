Bitrise CIビルドの後、テスト結果を一か所で確認できます。<GlossTerm baseform="workflow">Workflows</GlossTerm>内に複数のテスト<GlossTerm baseform="step">Steps</GlossTerm>がある場合でも、すべてのテストはビルドページで確認できます。Bitrise上でアクセスしやすく`actionable`なテスト結果を提供し、テストの失敗からより早く復旧でき、開発者体験全体を向上させることが目標です。


## テスト結果のデプロイ {#deploying-test-results}

最小限の設定で、テスト結果をビルドページにデプロイできます。必要な設定は環境によって異なります。

- テストの実行に公式のBitriseテストStepsを使用する場合
- テストの実行にその他のStepsを使用する場合

### 公式のBitriseテストStepsからの結果のデプロイ {#deploying-results-from-the-official-bitrise-testing-steps}

サポートされているテストStepsは次のとおりです。

- <strong>Android Unit Test</strong>: [Androidユニットテスト](/bitrise-ci/testing/testing-android-apps/android-unit-tests)。
- <strong>Android Instrumented Test</strong>: [Androidアプリのインストルメンテッドテストの実行](/bitrise-ci/testing/testing-android-apps/running-instrumented-tests-for-android-apps)。
- <strong>Xcode Test for iOS</strong>: [iOSアプリのユニットテストとUIテストの実行](/bitrise-ci/testing/testing-ios-apps/running-unit-and-ui-tests-for-ios-apps)。
- <strong>iOS Device Testing</strong>: [iOSのデバイステスト](/bitrise-ci/testing/device-testing-with-firebase/device-testing-for-ios)。
- <strong>Virtual Device Testing for Android</strong>: [Androidのデバイステスト](/bitrise-ci/testing/device-testing-with-firebase/device-testing-for-android)。
- <strong>Flutter Test</strong>: [Flutterアプリのテスト](/bitrise-ci/testing/testing-flutter-apps/running-the-dart-analyzer-on-bitrise)。

これらのStepsのいずれかを使用する場合は、Workflowに<strong>Deploy to Bitrise.io</strong>Stepが含まれていることを確認してください。Bitriseが、テスト結果をビルドページに自動的にデプロイします。

:::important[添付ファイルと不安定なテスト]

テストが添付ファイルを生成する場合、またはBitriseに不安定なテストを表示したい場合は、<strong>Deploy to Bitrise.io</strong>Stepのバージョンが 2.19.1 以降である必要があります。ファイル名によって添付ファイルをテストケースに関連付けるには、バージョン 2.26.0 以降が必要です。詳しくは[テストケース名に基づく添付ファイルの命名](#naming-attachments-after-their-test-case)を参照してください。

:::

### その他のStepsからの結果のデプロイ {#deploying-results-from-other-steps}

他のStepsを使用してテストを実行する場合(たとえば、完全にカスタムのテストソリューションとして[Script](https://bitrise.io/integrations/steps/script)Stepsを使用できます)は、追加の設定が必要です。

1. テストを実行するStepをWorkflowに追加します。
1. <strong>Export test results to the Test Reports</strong>StepをWorkflowに追加します。
1. Stepを設定します。詳しくは[Export test results to the Test Reports Stepの使用](/bitrise-ci/testing/deploying-and-viewing-test-results#using-the-export-test-results-to-test-reports-step)を参照してください。
1. Workflowに<strong>Deploy to Bitrise.io</strong>Stepが含まれていることを確認します。

   :::important[添付ファイルと不安定なテスト]

   テストが添付ファイルを生成する場合、またはBitriseに不安定なテストを表示したい場合は、<strong>Deploy to Bitrise.io</strong>Stepのバージョンが 2.19.1 以降である必要があります。ファイル名によって添付ファイルをテストケースに関連付けるには、バージョン 2.26.0 以降が必要です。詳しくは[テストケース名に基づく添付ファイルの命名](#naming-attachments-after-their-test-case)を参照してください。

   :::


## テスト結果の表示 {#viewing-test-results}

:::note[リッチHTMLレポート]

[リッチHTMLテストレポート](/bitrise-ci/testing/testing-ios-apps/viewing-xcode-test-results-in-rich-html-format)を使用している場合でも、<strong>Artifacts</strong>タブでそれらを確認できます。

:::

結果を表示するには、ビルドページを開き、<strong>Tests</strong>タブを選択します。テストはステータスに応じて異なるタブに分類されます。

- 失敗
- 合格
- スキップ
- エラー
- 不安定

デフォルトでは、Bitriseに失敗したテストの一覧が表示されます。各カテゴリ内でテスト実行の詳細を確認できます。

任意のテストをクリックすると、テストの所要時間、出力、生成された添付ファイルなどの詳細を確認できます。失敗のデバッグを容易にするため、テストレポートは添付された画像ファイルを関連するテストケースと並べて表示します。

:::note[サポートされているファイル形式]

現在、添付ファイルについては次のファイル形式をサポートしています。

`.jpg, .jpeg, .png, .txt, .log, .mp4, .webm, .ogg`

:::

不安定なテストは<strong>Flaky</strong>タブで確認できます。不安定なテストとは、コードに変更がなくても失敗したり成功したりするテストのことです。テストが失敗した後に[自動リトライ](/bitrise-ci/testing/testing-ios-apps/running-unit-and-ui-tests-for-ios-apps#test-repetitions)で成功した場合、Bitriseはそのテストを不安定としてマークし、<strong>Flaky</strong>タブで確認できます。また、テストの各リトライの詳細と添付ファイルも表示されます。不安定なテストの検出方法や、必要に応じてそれらを隔離する方法については、[Detecting and quarantining flaky tests](/bitrise-ci/testing/detecting-and-quarantining-flaky-tests)で詳しく説明しています。

![test-run.png](/img/_paligo/uuid-53eba539-6b4d-b4cf-c33d-6168fca79640.png)

テストレポートは、JUnitにおける`system-out`タグの使用もサポートしています。テストケースにこのタグが含まれている場合、その内容が<strong>Test output</strong>タブに表示されます。テストケースに`system-out`タグがあり、かつエラーメッセージも生成される場合は、両方が表示されます。


## テスト添付ファイルとテスト結果の照合 {#collating-test-attachments-with-test-results}

多くのテストが画像ファイルを生成します(スクリーンショットテスト、XCUITest など)。Bitriseは、これらの添付ファイルを関連するテストケースの下に表示できるため、ビルドページの<strong>Tests</strong>タブで確認できます。テスト添付ファイルとテスト結果をどのように照合するかは、使用しているテストツールと、`xcresult`ファイルを生成するかどうかによって異なります。

- テストが`xcresult`ファイルを生成する場合、Bitriseが添付ファイルをテストケースと自動的に照合します。追加の設定は不要です。
- テストが`xcresult`ファイルを生成しない場合は、次のいずれかを行えます。
    - 各ファイルにテストケース名を付ける: [テストケース名に基づく添付ファイルの命名](#naming-attachments-after-their-test-case)。
    - JUnit XML 内で各ファイルを参照する: [JUnit XML での添付ファイルの参照](#referencing-attachments-in-the-junit-xml)。

:::note[サポートされているファイル形式]

現在、添付ファイルでは次のファイル形式をサポートしています。

`.jpg, .jpeg, .png, .txt, .log, .mp4, .webm, .ogg`

:::

### テストケース名に基づく添付ファイルの命名 {#naming-attachments-after-their-test-case}

スクリーンショット、録画、ログに、それを生成したテストケースの名前を付けると、Bitriseが<strong>Tests</strong>タブのそのテストの下に表示します。

:::important[Stepのバージョン]

これには、<strong>Deploy to Bitrise.io</strong>Stepのバージョン 2.26.0 以降が必要です。<strong>Export test results to Test Reports</strong>Stepを使用する場合は、バージョン 1.3.0 以降が必要です。

:::

次の作業が必要です。

- [正しいファイル名の構造を使用する](#about-the-filename-structure)。
- [添付ファイルに正しい名前が付くようにテストツールを設定する](#setting-up-your-test-tool)。
- [Bitrise Stepを使用して添付ファイルをエクスポートする](#exporting-the-attachments)。

#### ファイル名の構造について {#about-the-filename-structure}

ファイル名は次の構造にする必要があります。

```text
<classname>__<name>[__run<k>]__<label>.<ext>
```

例: `com.example.LoginTest__emptyState__1.png`。

正しいファイル名を取得するには、次のようにします。

- JUnit XML の`<testcase>`要素から`classname`と`name`をコピーし、`" * / : < > ? \ |`の文字を`_`に置き換えます。Bitriseは JUnit XML 内の名前にも同じ置換を適用するため、どちらの表記でも一致します。
- 常にカウンターなどのラベルを追加してください。ラベルには`__`を含めることも、`_`で始めることもできません。
- 同じテストを複数のデバイスで実行する場合は、ラベルにデバイスを含めます(例: `api34_1`)。そうしないと、同じ名前のファイルはスキップされ、添付ファイルが表示されません。
- 同じテストケースの後続の実行にファイルを添付するには、ラベルの前に`__run2`、`__run3`などを追加します。

#### テストツールの設定 {#setting-up-your-test-tool}

テスト構成で、命名を一度だけ設定します。次の例では、いくつかの一般的なテストツールでの設定方法を示します。

<Tabs>
<TabItem value="espresso" label="Espresso" default>

Espresso のチェックが失敗したときにスクリーンショットを撮影する`RunListener`を登録します。

```kotlin
// app/build.gradle.kts
android {
    defaultConfig {
        testInstrumentationRunnerArguments["listener"] = "com.example.testing.BitriseScreenshotListener"
        testInstrumentationRunnerArguments["useTestStorageService"] = "true"
    }
}

dependencies {
    androidTestUtil("androidx.test.services:test-services:1.6.0")
}
```

```kotlin
// app/src/androidTest/java/com/example/testing/BitriseScreenshotListener.kt
package com.example.testing

import android.content.res.Resources
import android.os.Build
import androidx.test.core.app.takeScreenshot
import androidx.test.core.graphics.writeToTestStorage
import androidx.test.espresso.Espresso
import androidx.test.espresso.base.DefaultFailureHandler
import androidx.test.platform.app.InstrumentationRegistry
import org.junit.runner.Description
import org.junit.runner.notification.RunListener

private fun clean(value: String) = value.replace(Regex("""["*/:<>?\\|]"""), "_")

class BitriseScreenshotListener : RunListener() {
    override fun testStarted(test: Description) {
        val default = DefaultFailureHandler(InstrumentationRegistry.getInstrumentation().targetContext)
        Espresso.setFailureHandler { error, viewMatcher ->
            val screen = Resources.getSystem().displayMetrics.run { "${widthPixels}x$heightPixels" }
            val name = "${clean(test.className)}__${clean(test.methodName)}__api${Build.VERSION.SDK_INT}_${screen}_failure"
            takeScreenshot().writeToTestStorage(name)
            default.handle(error, viewMatcher)
        }
    }
}
```

通常の JUnit アサーションではスクリーンショットは取得されません。

<TabItem value="paparazzi" label="Paparazzi">

スナップショットハンドラーを追加する共有関数を通じて、Paparazzi のルールを作成します。ハンドラーは、すべてのスナップショットを添付ファイル名でも保存します。

```kotlin
// src/test/java/com/example/testing/BitrisePaparazzi.kt
package com.example.testing

import app.cash.paparazzi.DeviceConfig
import app.cash.paparazzi.HtmlReportWriter
import app.cash.paparazzi.Paparazzi
import app.cash.paparazzi.Snapshot
import app.cash.paparazzi.SnapshotHandler
import app.cash.paparazzi.SnapshotVerifier
import java.awt.image.BufferedImage
import java.io.File
import javax.imageio.ImageIO

private fun clean(value: String) = value.replace(Regex("""["*/:<>?\\|]"""), "_")

fun bitrisePaparazzi(deviceConfig: DeviceConfig = DeviceConfig.PIXEL_5) =
    Paparazzi(deviceConfig = deviceConfig, snapshotHandler = BitriseSnapshotHandler())

class BitriseSnapshotHandler(
    maxPercentDifference: Double = 0.1,
    private val delegate: SnapshotHandler =
        if (System.getProperty("paparazzi.test.verify") == "true") SnapshotVerifier(maxPercentDifference)
        else HtmlReportWriter(),
) : SnapshotHandler by delegate {
    override fun newFrameHandler(snapshot: Snapshot, frameCount: Int, fps: Int): SnapshotHandler.FrameHandler {
        val frames = delegate.newFrameHandler(snapshot, frameCount, fps)
        val test = snapshot.testName
        val label = snapshot.name?.replace(Regex("_+"), "_")?.removePrefix("_") ?: "snapshot"
        val name = "${clean("${test.packageName}.${test.className}")}__${clean(test.methodName)}__$label"
        val file = File(System.getProperty("paparazzi.build.dir"), "bitrise-snapshots/${System.getProperty("bitrise.test.task")}/$name.png")
        return object : SnapshotHandler.FrameHandler by frames {
            override fun handle(image: BufferedImage) {
                file.parentFile.mkdirs()
                ImageIO.write(image, "png", file)
                frames.handle(image)
            }
        }
    }
}
```

テストでは、`Paparazzi(...)`を`bitrisePaparazzi(...)`に置き換えます。次に、モジュールの`build.gradle.kts`に以下を追加します。1 つ目のブロックは、Android Gradleプラグイン 8 でハンドラーが`java.awt`を使用できるようにします。2 つ目のブロックは、各テストタスクに専用のフォルダーを割り当て、前回の実行のスナップショットを削除し、現在のスナップショットをbuild cacheに保持します。

```kotlin
tasks.withType<org.jetbrains.kotlin.gradle.tasks.KotlinJvmCompile>().configureEach {
    if ("UnitTest" in name) compilerOptions.noJdk.set(false)
}

tasks.withType<Test>().configureEach {
    val snapshots = layout.buildDirectory.dir("bitrise-snapshots/$name")
    systemProperty("bitrise.test.task", name)
    outputs.dir(snapshots)
    doFirst { snapshots.get().asFile.deleteRecursively() }
}
```

この例は Paparazzi 1.3.5 向けです。Paparazzi 2.0 では、`HtmlReportWriter(maxPercentDifference = maxPercentDifference)`を使用してレポートライターを作成してください。

Roborazzi を実行するたびに、Roborazzi のスクリーンショットを添付ファイル名でコピーします。

```kotlin
// app/build.gradle.kts
val bitriseScreenshots by tasks.registering(Sync::class) {
    from(layout.buildDirectory.dir("outputs/roborazzi")) { include("*.png") }
    into(layout.buildDirectory.dir("bitrise-screenshots"))
```

<TabItem value="detox" label="Detox">

Detox 設定の`artifacts.pathBuilder`をこのファイルに指定します。このファイルは、すべてのスクリーンショット、動画、ログに、jest-junit がデフォルト設定でテスト名を付ける方法と同じ名前を付けます。

```javascript
// e2e/bitrisePathBuilder.js
const path = require('path');

const clean = (value) => value.replace(/["*/:<>?\\|]/g, '_');

module.exports = class BitrisePathBuilder {
  constructor({ rootDir }) {
    this.rootDir = rootDir;
  }

  buildPathForTestArtifact(artifactName, testSummary) {
    if (!testSummary) return path.join(this.rootDir, artifactName);

    const { title, fullName } = testSummary;
    const key = clean(`${fullName.slice(0, -title.length).trim()} ${title}`);
    const ext = path.extname(artifactName);
    const label = path.basename(artifactName, ext).replace(/_+/g, '_').replace(/^_/, '');
    return path.join(this.rootDir, `${key}__${key}__${label}${ext}`);
  }
};
```

<TabItem value="playwright" label="Playwright">

junit レポーターの`includeProjectInTestName`を有効にし、各テストのスクリーンショットと動画を添付ファイル名でコピーするレポーターを追加します。

```typescript
// playwright.config.ts
reporter: [
  ['junit', { outputFile: 'test-results/junit.xml', includeProjectInTestName: true }],
  ['./bitrise-reporter.ts'],
],
use: { screenshot: 'only-on-failure', video: 'retain-on-failure' },
```

```typescript
// bitrise-reporter.ts
import fs from 'node:fs';
import path from 'node:path';
import type { Reporter, TestCase, TestResult } from '@playwright/test/reporter';

const clean = (value: string) => value.replace(/["*/:<>?\\|]/g, '_');
const supported = /\.(png|jpe?g|mp4|webm|ogg|txt|log)$/i;

export default class BitriseAttachments implements Reporter {
  onTestEnd(test: TestCase, result: TestResult) {
    const [, project, file, ...titles] = test.titlePath();
    const key = `${clean(file)}__${clean((project ? `[${project}] ` : '') + titles.join(' › '))}`;
    const files = result.attachments.filter((a) => a.path && supported.test(a.path));
    files.forEach((a, i) => {
      const label = (result.retry ? `retry${result.retry}_` : '') + (i + 1);
      const target = path.join('test-attachments', `${key}__${label}${path.extname(a.path!)}`);
      fs.mkdirSync(path.dirname(target), { recursive: true });
      fs.copyFileSync(a.path!, target);
    });
  }
}
```

#### 添付ファイルのエクスポート {#exporting-the-attachments}

:::important[Stepのバージョン]

これには、<strong>Deploy to Bitrise.io</strong>Stepのバージョン 2.26.0 以降が必要です。<strong>Export test results to Test Reports</strong>Stepを使用する場合は、バージョン 1.3.0 以降が必要です。

:::

<strong>Deploy to Bitrise.io</strong>Stepは常に必要です。このステップが、正しく命名された添付ファイルをテスト結果と一緒にデプロイします。それ以外に何が必要かは、テストを実行するStepによって異なります。

- <strong>公式のBitriseテストSteps</strong>: 追加の設定は不要です。<strong>Deploy to Bitrise.io</strong>Stepが、テスト結果と一緒に添付ファイルをエクスポートします。Stepsの一覧については、[公式のBitriseテストStepsからの結果のデプロイ](#deploying-results-from-the-official-bitrise-testing-steps)を参照してください。
- <strong>Other Steps</strong>(Script や npm Stepsなど): テストを実行するStepの後に<strong>Export test results to Test Reports</strong>Stepを追加します。このステップは添付ファイルを見つけて、<strong>Deploy to Bitrise.io</strong>Stepがデプロイ元とする場所に移動します。<strong>Test result base path</strong> 入力には、テスト結果と添付ファイルの両方を含むフォルダーを設定します(例: `app/build/`)。詳しくは[Export test results to Test Reports Stepの使用](#using-the-export-test-results-to-test-reports-step)を参照してください。

#### 添付ファイルが表示されない場合のトラブルシューティング {#troubleshooting-missing-attachments}

添付ファイルが表示されない場合は、ビルドログを確認してください。

- <strong>Export test results to Test Reports</strong>Stepは、複数のテストまたはファイルに一致する名前、無効な`__run`番号を持つ名前、またはラベルのない名前について警告をログに記録します。その他のスキップされたファイルは、詳細ログを有効にした場合にのみ表示されます。<strong>Enable verbose logging?</strong> 入力を`yes`に設定してください。
- <strong>Deploy to Bitrise.io</strong>Stepは、レポート内でテストケースにリンクできないすべてのファイルについて警告をログに記録します。

### JUnit XML での添付ファイルの参照 {#referencing-attachments-in-the-junit-xml}

ファイルにテストケース名を付けられない場合は、代わりに JUnit XML 内でファイルを参照します。

<Tabs>
<TabItem value="workflow-editor" label="Workflow Editor" default>

1. テストから`JUnit.xml`ファイルを生成します。

   ファイル構造の概要は、おおよそ次のようになります。

   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <testsuites time="15.682687">
       <testsuite name="Tests.Registration" time="6.605871">
           <testcase name="testCase1" classname="Tests.Registration" time="2.113871" />
       </testsuite>
   </testsuites>
   ```
1. 添付ファイルを`testcase`に関連付けるため、`<properties>`要素を追加します。

   要素の`name`属性には、`attachment_#`という形式の値を設定する必要があります。ここで`#`は添付ファイルの順序インデックスで、値はファイル名です。Bitriseは、添付ファイルのプロパティを持つすべてのテストの添付ファイルを表示しますが、失敗したテストにのみスクリーンショットを添付するのが最も一般的です。テストを失敗としてマークするには、`<failure>`要素を使用します。

   ```xml
   <testcase name="testCase1" classname="Tests.Registration" time="2.113871" />
     <failure message="Assertion error message" type="AssertionError">
       Call stack printed here
     </failure>
     <properties>
       <property name="attachment_1" value="pp1.jpg" />
       <property name="attachment_2" value="pp2.jpg" />
     </properties>            
   </testcase>
   ```

## Export test results to Test Reports Stepの使用 {#using-the-export-test-results-to-test-reports-step}

<strong>Export test results to Test Reports</strong>Stepを使用すると、結果を自動的にエクスポートしないStepsを使用している場合でも、テスト結果が<strong>Tests</strong>タブに確実に表示されるようにできます。

正しく設定すると、Stepがプロジェクトのリポジトリ内でテスト結果を見つけ、エクスポートディレクトリに配置します。

1. <Partial_OpeningTheWorkflowEditor />
1. テストを実行するStepの後に、<strong>Export test results to Test Reports</strong>StepをWorkflowに追加します。
1. <strong>The name of the test</strong>入力に、the name of the testの実行を設定します。
1. <strong>Test result base path</strong> 入力に、テスト結果が格納されているパスを設定します。

   ![Managing_an_app_s_bitrise.png](/img/_paligo/uuid-fd13332e-571f-e706-88ed-a20a29db7aea.png)

   ここにはフォルダーを設定することをおすすめしますが、特定のファイルパスを設定することもできます。default valueは、プロジェクトのソースディレクトリです。パターンの例を示します。

   - プロジェクトのルートディレクトリが`app`の場合: `app/build/test-results/testDemoDebugUnitTest/`
   - テスト結果がプロジェクトフォルダー内にあるものの、`app`がルートディレクトリではない場合: ./app/build/test-results/testDemoDebugUnitTest/

   [テストケース名に基づいて命名された添付ファイル](/bitrise-ci/testing/deploying-and-viewing-test-results#naming-attachments-after-their-test-case)をエクスポートするには、テスト結果と添付ファイルの両方を含むフォルダーを設定します(例: `app/build/`)。
1. <strong>Test result search pattern</strong>入力に、テスト結果ファイルに一致するパターンを設定します。

   この検索パターンは、<strong>Path where custom test results reside</strong> 入力に設定したパス内のすべてのファイルとフォルダーを検索するために使用されます。

   複数のファイルに一致した場合、Stepは最初に一致したファイルをエクスポートし、ログに警告を出力します。前の入力で特定のファイルパスを設定した場合は、ここには * を設定してください。

   パターンの例:

   - ベースパス内のすべてのファイルに一致させる: `*`
   - ベースパス内の特定のディレクトリにあるすべてのファイルに一致させる: `*/build/test-results/testDemoDebugUnitTest/*`
   - ベースパスが`app/build/`のような広いフォルダーの場合に、単一の JUnit XML に一致させる: `*/test-results/testDemoDebugUnitTest/TEST-com.example.ScreenshotTest.xml`
1. <strong>Step’s test result directory</strong> 入力で、パスが正しいことを確認します。

   この入力の値は変更しないでください。これは、<strong>Deploy to Bitrise.io</strong>Stepがエクスポートするテスト結果を探すフォルダーです。`$BITRISE_TEST_RESULT_DIR`環境変数に設定されている必要があります。
1. Workflowに<strong>Deploy to Bitrise.io</strong>Stepが含まれていることを確認します。

   テストが添付ファイルを生成する場合は、Stepのバージョンが 2.19.x 以降であることを確認してください。
