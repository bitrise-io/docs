Bitrise Build Cacheをローカルの Bazel ビルドにも使用できます。ローカルビルドは、CIビルドと同じキャッシュを読み取るため、CIがすでに実行したアクションを、お使いのマシンで再度実行する必要はありません。

Bitrise Build Cache CLIは、キャッシュフラグを`~/.bazelrc`に書き込むことで、この設定を行います。

手順を手動で進める代わりに、AIコーディングエージェントを使って設定することもできます。[Getting started with AI](/bitrise-build-cache/getting-started-with-the-build-cache/getting-started-with-ai)を参照してください。

## 始める前に {#before-you-start}

次のものを用意してください。
- お使いのマシン上の、Bazel 6 以降で動作する Bazel プロジェクト。この設定では Bazel の credential helper サポートを使用しますが、これより前のバージョンにはありません。
- Build Cacheが有効になっているBitrise workspace。[Build Cacheページ](https://app.bitrise.io/build-cache/)で確認できます。
- マシンがVPN、ファイアウォール、または送信プロキシの内側にある場合は、Build Cacheが使用するBitriseホストへのネットワークアクセス。[Network endpoints for firewalls and VPNs](/bitrise-build-cache/getting-started-with-the-build-cache/network-endpoints-for-firewalls-and-vpns)を参照してください。

:::important[アクティベートはプロジェクトごとではなくグローバルです]

`activate bazel`は、ホームディレクトリの`~/.bazelrc`に単一のブロックを書き込みます。プロジェクトの`.bazelrc`には一切変更を加えません。

アクティベートを実行したプロジェクトだけでなく、お使いのマシン上のすべての Bazel プロジェクトがキャッシュフラグを使用します。ダッシュボードに報告されるリポジトリのURLは、アクティベートを実行したディレクトリの git リモートから読み取られるため、複数の Bazel プロジェクトがあるマシンでは、すべてが最初のプロジェクトとして報告されます。これはダッシュボードでの帰属にのみ影響し、キャッシュの正確性には影響しません。変更するには、別のプロジェクトのディレクトリでアクティベートを再実行してください。

:::

## CLIのインストール {#installing-the-cli}

Homebrew でCLIをインストールします(<strong>推奨</strong>)。

```bash
brew install bitrise-io/bitrise-build-cache/bitrise-build-cache
```

Homebrew を使用しない場合は、次のようにします。

```bash
curl --retry 5 -sSfL \
  'https://raw.githubusercontent.com/bitrise-io/bitrise-build-cache-cli/main/install/installer.sh' \
  | sh -s -- -b ~/.local/bin
```

インストール先が`PATH`に含まれていることを確認し、インストールを確認してください。

```bash
bitrise-build-cache --version
```

その後も、CLIを`PATH`に含めたままにしてください。Bazel は、セットアップ時だけでなく、ビルドのたびにCLIを実行して新しい認証トークンを取得します。

## キャッシュのアクティベート {#activating-the-cache}

対話型ウィザードを実行します。

```bash
bitrise-build-cache activate --interactive
```

ウィザードでは、次の項目が求められます。

1. <strong>Sign in to Bitrise</strong>: 初回の実行時に、認証のためにブラウザーが開きます。CLIは認証情報をOSのキーチェーンに保存し、自動的に更新するため、2回目以降はこの手順をスキップします。使用可能なキーチェーンがないマシンでは、CLIは設定ファイルへの保存に切り替わります。
1. <strong>Select a workspace</strong>: 使用するBuild Cacheを持つworkspaceを選択します。アクセスできるものが1つだけの場合、CLIが自動的に選択します。
1. <strong>Which build tools should I set up</strong>: <strong>Bazel</strong>が選択されていることを確認してください。スペースキーでオプションを切り替え、Enter キーで確定します。
1. <strong>Cache for all projects, or only opted-in ones?</strong>: このマシンに複数のプロジェクトがあり、一部のプロジェクトだけでキャッシュを使用したい場合を除き、デフォルトの <strong>Always</strong> のままにします。[Per-project cache scoping](/bitrise-build-cache/getting-started-with-the-build-cache/per-project-cache-scoping)を参照してください。
1. <strong>Display name for this machine's local invocations</strong>: ローカルビルドがBuild Cacheダッシュボードに表示される名前です(例: `local-<yourhandle>`)。
1. <strong>Enable cache push</strong>: デフォルトの <strong>Yes, push too</strong> のままにします。[Cache push mode](#cache-push-mode)を参照してください。

サインイン済みの場合の非対話型の同等のコマンドは、次のとおりです。

```bash
bitrise-build-cache activate bazel --cache
```

### アクティベートが書き込む内容 {#what-the-activation-writes}

`~/.bazelrc`の末尾に、マーカー付きのブロックが1つ追加されます。既存の内容は保持され、アクティベートを再実行した場合はこのブロックのみが更新されます。

```bash
# [start] generated-by-bitrise-build-cache
build --credential_helper=*.services.bitrise.io=bitrise-build-cache
build --remote_cache=grpcs://bitrise-accelerate.services.bitrise.io
build --remote_timeout=600s
build --remote_header=x-flare-buildtool=bazel
build --remote_header=x-flare-builduser=
build --remote_upload_local_results
build --bes_backend=grpcs://flare-bes.services.bitrise.io:443
build --bes_results_url=https://app.bitrise.io/build-cache/invocations/bazel/
build --bes_timeout=2m
build --bes_upload_mode=wait_for_upload_complete
build --build_event_publish_all_actions
build --show_timestamps
build --remote_header='x-org-id=<workspace-id>'
build --bes_header='x-org-id=<workspace-id>'
build --remote_header='x-repository-url=https://github.com/<org>/<repo>.git'
build --bes_header='x-repository-url=https://github.com/<org>/<repo>.git'
build --bes_header='x-os=<detailed OS info>'
build --bes_header='x-locale=C'
build --bes_header='x-default-charset=UTF-8'
build --bes_header='x-cpu-cores=4'
build --bes_header='x-mem-size=16759259136'
# [end] generated-by-bitrise-build-cache
```

特に注目すべき2行があります。

- `--credential_helper`は、トークンを保存する代わりにCLIを指しています。そのため、Bazel はビルドのたびに新しいトークンを取得し、期限切れが近いログインでも動作し続けます。これが、CLIを`PATH`に含めておく必要がある理由です。
- `--remote_upload_local_results`はプッシュモードで、デフォルトの設定です。`--cache-push=false`を指定してアクティベートすると、代わりに`--noremote_upload_local_results`が書き込まれます。

`x-os`、`x-cpu-cores`、`x-mem-size`、`x-locale`、`x-default-charset`の各ヘッダーはお使いのマシンの情報を表し、分析にのみ使用されます。cache keysには影響しません。これらはブロックを生成したマシンに固有であるため、設定をコミットする場合は注意が必要です。[What is safe to commit](#what-is-safe-to-commit)を参照してください。

## ビルドの実行 {#running-a-build}

1. 最初に`bazel clean`を実行します。Bazel のローカルアクションキャッシュはリモートキャッシュの手前にあるため、ターゲットがすでにローカルでビルドされている場合、Bazel はディスクから結果を返し、Bitriseに接続しません。その結果、リモートキャッシュが動作している証拠は得られません。

   ```bash
   cd path/to/your/bazel/project
   bazel clean
   ```

1. ターゲットをビルドします。

   ```bash
   bazel build //your/target:name
   ```

ウォームキャッシュにヒットしたビルドは、次のように終了します。

```bash
(16:47:35) INFO: Invocation ID: <invocation-id>
(16:47:35) INFO: Streaming build results to: https://app.bitrise.io/build-cache/invocations/bazel/<invocation-id>
(16:47:36) INFO: Analyzed target //src/close-matching-prs:close-matching-prs (91 packages loaded, 9216 targets configured).
(16:47:36) INFO: Found 1 target...
(16:47:36) INFO: Elapsed time: 0.934s, Critical Path: 0.18s
(16:47:36) INFO: 11 processes: 4 remote cache hit, 7 internal.
(16:47:36) INFO: Build completed successfully, 11 total actions
```

## 動作の確認 {#checking-that-it-worked}

サマリー行が確認の根拠になります。次の3つのケースで表示が異なります。

| サマリー行 | 意味 |
|---|---|
| `11 processes: 4 remote cache hit, 7 internal.` | 正常に動作しています。アクションはBitrise Build Cacheから取得されました。 |
| `1 process: 4 action cache hit, 1 internal.` | ローカルキャッシュから返されました。リモートキャッシュには接続していないため、最初に`bazel clean`を実行してください。 |
| `11 processes: 7 internal, 4 processwrapper-sandbox.` | ローカルで最初からビルドされました。このターゲットに対するキャッシュのエントリがないか、認証に失敗しています。出力の前のほうで`WARNING: Remote Cache: UNAUTHENTICATED`を探してください。 |

`internal`アクション(シンボリックリンクやファイルの書き込みなど)は、キャッシュできません。重要なのは、内部アクションを除いたアクションに対するリモートキャッシュヒットの比率です。

| 項目 | 確認場所 | 成功時の状態 |
|---|---|---|
| `INFO: N processes: X remote cache hit` | Bazel のビルドサマリー | `bazel clean`後に、`remote cache hit`の数が0以外になる |
| `INFO: Streaming build results to:` | ビルドの最初と最後の行 | 呼び出しへのリンクが表示される |
| ダッシュボード | 表示されたリンク、または[Build Cacheページ](https://app.bitrise.io/build-cache/) | 同じヒット数で、表示名の下に行が表示される |

## キャッシュプッシュモード {#cache-push-mode}

このガイドの設定では、キャッシュプッシュを有効にしてBuild Cacheをアクティベートします。ローカルビルドは共有キャッシュの読み取りと書き込みの両方を行います。お使いのマシンが実行したすべてのアクションは、チームメンバーやCIが再利用できるエントリになり、操作内容は[Build Cacheページ](https://app.bitrise.io/build-cache/)に表示されます。

ローカルビルドでキャッシュの読み取りのみを行いたい場合は、以下の[Opting into pull-only mode](#opting-into-pull-only-mode)を参照してください。

## プルのみモードの選択 {#opting-into-pull-only-mode}

チームがすでにCIからキャッシュを生成していて、ローカルビルドではキャッシュの読み取りのみを行いたい場合は、キャッシュプッシュをオフにします。ただしその場合、ローカルビルドはキャッシュに何も追加しません。そのため、CIがまだ実行されていないと、サマリー行には引き続き`0 remote cache hit`と表示されます。

`bitrise-build-cache activate --interactive`を再実行し、キャッシュプッシュのプロンプトで <strong>No, pull only</strong> を選択するか、非対話型のアクティベートコマンドを実行します。

```bash
bitrise-build-cache activate bazel --cache --cache-push=false
```

ビルドを実行せずに、現在のモードを確認できます。

```bash
grep upload_local_results ~/.bazelrc
# --remote_upload_local_results    → push enabled (default)
# --noremote_upload_local_results  → pull-only
```

## 設定のリポジトリへのコミット {#committing-the-configuration-to-your-repository}

Bazel は、workspaceのルートにある`.bazelrc`をすでに読み取ります。そのため、キャッシュフラグをマシンごとに生成する代わりに、リポジトリにコミットできます。これにより、開発マシンのオンボーディングは、CLIのインストールとサインインだけで済みます。

```bash
brew install bitrise-io/bitrise-build-cache/bitrise-build-cache
bitrise-build-cache auth login
```

### ファイルの組み合わせ方 {#how-the-files-combine}

Bazel は次の順序で設定ファイルを読み取り、単一値のフラグでは最後の値が優先されます。

1. システムファイル: `/etc/bazel.bazelrc`
1. workspaceファイル: `<repo>/.bazelrc`(コミットされたもの)
1. ホームファイル: `~/.bazelrc`(アクティベートが実行された場合に書き込まれるもの)
1. コマンドラインフラグ

そのため、ホームファイルはコミットされたファイルより優先され、コマンドラインフラグはその両方より優先されます。Bazel が実際に読み込んだ内容を確認するには、ビルドに`--announce_rc`を追加します。

### アクティベートを実行しない開発者にプルのみを強制する {#force-pull-only-for-developers-who-dont-run-the-activation}

CLIをインストールして`auth login`を実行するだけの開発者には、`~/.bazelrc`が作成されないため、コミットされたブロックを上書きするものがありません。CLIのデフォルトに関係なく、これらの開発者にキャッシュの読み取りのみを行わせたい場合は、プルのみのフラグをコミットします。

```bash
build --noremote_upload_local_results
```

CIでは、アクティベートを実行します。CLIはプッシュ有効のフラグを`~/.bazelrc`に書き込みます。ホームファイルはコミットされたworkspaceファイルより優先されるため、そのマシンに限り、コミットされたプルのみのフラグが上書きされます。

```bash
bitrise-build-cache activate bazel --cache
```

これにより、開発者ごとの設定なしで役割を分けられます。コミットされたファイルは、アクティベートを省略した開発者が引き継ぐプルのみのデフォルトとなり、キャッシュに書き込むべき環境がアクティベートを実行する環境となります。

### コミットしても安全なもの {#what-is-safe-to-commit}

| 行 | コミット | 理由 |
|---|---|---|
| `--remote_cache`, `--remote_timeout`, `--bes_backend`, `--bes_results_url`, `--bes_timeout`, `--bes_upload_mode`, `--build_event_publish_all_actions`, `--show_timestamps` | はい | すべてのマシンで同一です |
| `--remote_header='x-org-id=…'` と対応する `--bes_header` | はい | Workspace全体で共通であり、マシン固有ではありません |
| `--remote_header='x-repository-url=…'` と対応する `--bes_header` | はい | このリポジトリを識別します |
| `--noremote_upload_local_results` | 任意: アクティベートを省略する開発者にプルのみを強制したい場合 | `auth login`のみを実行するすべての開発者に引き継がれます。CIでアクティベートを実行すると、`~/.bazelrc`に`--remote_upload_local_results`が書き込まれ、そのマシンではコミットされた値が上書きされます |
| `--credential_helper=*.services.bitrise.io=bitrise-build-cache` | はい(値を確認してから) | Bazel が`PATH`から検索する、バイナリ名のみの形式です。CLIが`PATH`に含まれていないマシンでアクティベートを実行した場合、CLIは代わりに絶対パスを書き込みます。その形式はコミットしないでください |
| `--bes_header='x-os=…'`, `x-cpu-cores`, `x-mem-size`, `x-locale`, `x-default-charset` | いいえ | マシンごとに異なり、`x-os`にはホスト名が含まれます。これらは分析にのみ使用され、cache keysには影響しませんが、コミットすると全員のビルドがお使いのマシンに帰属されてしまいます |
| `--remote_header=authorization="Bearer …"` | 絶対にコミットしない | 有効な認証情報です。CIで生成されたブロックにのみ表示されます |

### CLIがインストールされていない場合の動作 {#what-happens-without-the-cli-installed}

`--credential_helper`の行をコミットした場合、CLIをインストールしていないチームメンバーはビルドをまったく実行できません。Bazel は`PATH`からヘルパーを検索しますが見つからず、リモートキャッシュの初期化中に失敗します。

```bash
ERROR: Could not find file with name 'bitrise-build-cache' on PATH '...'
ERROR: Could not find file with name 'bitrise-build-cache' on PATH '...'
ERROR: Could not find file with name 'bitrise-build-cache' on PATH '...'
ERROR: Error initializing RemoteModule
```

Bazel はコード2で終了し、ターゲットはビルドされません。失敗はビルドの開始前に発生するため、ローカルビルドへのフォールバックはありません。

そのマシンにCLIをインストールして`bitrise-build-cache auth login`を実行すると、解決します。

## Remote Build Execution

workspaceで Remote Build Execution が有効になっている場合は、アクティベートに`--rbe`フラグを追加することで、ローカルでも使用できます。その前に、workspace用のワーカーと、リポジトリの`.bazelrc`にあるプール設定を済ませておく必要があります。[Remote Build Execution for Bazel](/bitrise-build-cache/build-cache-for-bazel/remote-build-execution-for-bazel)を参照してください。

## トラブルシューティング {#troubleshooting}

まず、CLIのヘルスチェックから始めます。ローカル設定のすべての部分を検査し、自動で修復できる問題を修復します。

```bash
bitrise-build-cache doctor --fix --interactive
```

それでも問題が解決しない場合は、次の表を確認してください。

| 問題 | 対処 |
|---|---|
| ウィザードがターミナルを必要とすると報告される | 行ベースのモードにするには、`TERM=dumb bitrise-build-cache activate --interactive`を実行してください。 |
| ビルドで`remote cache hit`ではなく`action cache hit`と報告される | Bazel がリモートキャッシュから取得するように、`bazel clean`を実行してください。 |
| ビルドが`Could not find file with name 'bitrise-build-cache' on PATH`で失敗する | CLIがインストールされていないか、`PATH`に含まれていません。インストールしてから`bitrise-build-cache auth login`を実行してください。 |
| 認証情報の取得中にビルドが失敗し、credential helper の名前が表示される | CLIはインストールされていますが、認証情報がありません。`bitrise-build-cache auth login`を実行してください。 |
| `doctor`が自動で修復できない問題を報告する | 詳細なコンテキストを確認するには、`--debug`を付けて再実行してください。 |
| ビルドがキャッシュに到達できない、またはキャッシュの呼び出しがタイムアウトする | VPN、ファイアウォール、またはプロキシがBitriseホストをブロックしている可能性があります。[Network endpoints for firewalls and VPNs](/bitrise-build-cache/getting-started-with-the-build-cache/network-endpoints-for-firewalls-and-vpns)と照らし合わせて確認してください。 |
