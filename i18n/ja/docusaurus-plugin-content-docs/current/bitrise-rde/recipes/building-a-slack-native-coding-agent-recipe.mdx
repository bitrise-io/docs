このレシピでは、Slackネイティブなコーディングエージェントのアーキテクチャについて説明します。チケットをアサインするか、スレッドで@メンションするだけで、エージェントは要件を読み取り、プランを投稿し、使い捨ての開発マシンを起動し、コードを書いてテストし、プルリクエストを作成し、届いたレビューコメントやCIの結果に対応し、プルリクエストがマージされると自身の後片付けを行います。

中心となる考え方は関心の分離です。小規模でロックダウンされたオーケストレーターがSlack内で動作し、コードに直接触れることはありません。実際のコーディングはすべて、使い捨ての<GlossTerm baseform="remote dev environment">Remote Dev Environments</GlossTerm>（RDE）に委任されます。このアーキテクチャのオープンソースのリファレンス実装である <strong>bitclaw</strong> は、[github.com/bitrise-io/bitclaw-public](https://github.com/bitrise-io/bitclaw-public) で公開されています。詳細は、以下の[リファレンス実装](#reference-implementation)を参照してください。

## エージェントが行うこと {#what-the-agent-does}

Slackでエージェントに送られる典型的なリクエストの例です。

- すでに完全にロールアウトされたフィーチャーフラグを整理する。
- 停滞しているプルリクエストを、CIがグリーンになるまで進める。
- 以前のプルリクエストをパターンの参考にして、依存関係をアップグレードする。
- サポートチケットを調査する。
- 監視ツールに表示されたエラーメッセージに、より多くのコンテキストを追加する。

エージェントのユーザーにチケットをアサインするだけで、作業を開始できます。エージェントは共有チャンネルに短い確認メッセージを投稿し、その後はマイルストーン（プラン作成、開発セッションの作成、コードのプッシュ、プルリクエストの作成、CIの結果、レビューフィードバックへの対応、マージ、後片付けの完了）でのみスレッドを更新します。中間のステップをいちいち説明することはありません。

プルリクエストとチケットはどちらも、それらを所有するスレッドに紐づけられているため、レビューコメント、CIの結果、チケットのステータス遷移は発生するたびにセッションへと反映されます。エージェントはこれらのイベントに自律的に反応し、レビュアーのフィードバックに対応し、チケットへのフォローアップの質問に回答し、マージが完了すると開発環境を破棄してチケットのステータスを遷移させます。

同じループは、より大規模で長期にわたる作業にも対応できます。たとえば、数日にわたり複数回のマージコンフリクトが発生するような複数ファイルにまたがるリファクタリングでも、人間に求められるのは定期的なレビューだけです。

## カスタムオーケストレーターを構築する理由 {#why-build-a-custom-orchestrator}

このようなエージェントは、ソースコード、認証情報、チケットトラッカー、そして（公開リポジトリの場合は）オープンなインターネットといった、機密性の高いあらゆるものに同時に触れます。汎用的な既製のエージェントでは、特定のチームにとってエージェントを信頼できるものにする要素、たとえばどの作成者の発言を受け入れるか、どのアクションに人間の承認が必要か、ワークフロー上で「完了」が何を意味するかといった点を組み込むことはできません。

オーケストレーターを自前で持つことで、これらすべてを自分たちで制御できるコードとして保持できます。エージェントがどのツールを持つか、システムプロンプトの指示ではなく実行可能なチェックとして書かれた信頼ルール、そして実際のチームの働き方に合わせて調整されたワークフローです。

オーケストレーター自体は大規模である必要はありません。単一の小さなサービスで十分であり、コードを実行するのではなく中継・計画・ツール呼び出しだけを行うため、後に他のタスクに対して実行することになる委任・レビュー・マージのループを使って、コーディングエージェント自身にブートストラップさせるのにも適した対象です。

## 中核となる原則：オーケストレーターはコードを書かない {#core-principle-the-orchestrator-cant-code}

この設計には、根幹を支える1つのルールがあります。<strong>オーケストレーターはコーダーではない</strong>、ということです。

- 1つのSlackスレッドが1つのセッションであり、1つの永続的な会話によって支えられているため、メッセージやウェブフック、数日後に届くフォローアップの間でコンテキストが失われることはありません。
- すべての機能は、狭くスコープされたツールとして用意されています。Slackへの投稿、プルリクエストの読み取りと管理、チケットトラッカーの読み取り、ログやメトリクスを取得するためのオブザーバビリティツールへの問い合わせ、そしてRDEセッションの作成と操作です。
- Pull requestsとチケットは、それらを所有するスレッドに紐づけられているため、レビューコメント、CIの結果、チケットのステータス遷移は、適切な会話内のメッセージとして届きます。エージェントはイベントをポーリングするのではなく、イベントに反応します。
- オーケストレーターにはシェルもファイルアクセスもありません。コードを実行することはできず、チケットトラッカーやソースコード管理のAPIを通じてソースコードを読み取ることもできません。これらのツールは、プロンプトではなくコード上で拒否します。

```
 Ticket assignment ────┐
 Slack @mention ───────┼──► one Slack thread = one session (the orchestrator)
 Webhooks (PR, CI) ────┘        │                          ▲
                                │ creates and drives        │ review, CI, and ticket
                                ▼                           │ events route back
                        RDE session ───── git push ──► pull request
                        (coding agent + full toolchain)
```

## Remote Dev Environmentsの役割 {#where-remote-dev-environments-fit}

リポジトリのクローン、パッケージのインストール、ビルドツールやテストスイートの実行、`Makefile`に書かれている内容の実行など、コーディングエージェントに必要なものはすべて、オーケストレーターの認証情報を保持するマシン上では実行すべきではないものばかりです。代わりに、各タスクに専用の使い捨てマシンを割り当てます。

- <strong>1つのテンプレート、1回のツール呼び出し。</strong> すべてのコーディング用マシンを、固定された単一の<GlossTerm baseform="rde template">テンプレート</GlossTerm>から作成します。スタック、マシンタイプ、そしてコーディングエージェントをインストールし、git専用のSSHIDを設定し、永続的なターミナルセッションでエージェントを起動するウォームアップスクリプトです。認証情報は<GlossTerm baseform="saved input">saved inputs</GlossTerm>とセッション入力経由で渡します。暗号化されており、イメージに焼き込まれることはありません。
- <strong>付き添いではなく、ブリーフィングを。</strong> 各セッションは、リポジトリ、チケット、受け入れ基準、ブランチルールを含む自己完結型のタスクブリーフィングとともに作成します。これに加えて、1つの行動指針を与えます。入力待ちでブロックしないこと、最も説明のつくデフォルトを選び、その前提をコミットメッセージとpull request descriptionに記録し、作業を続けることです。誤った前提が修正されるのは、プルリクエストのレビューの場です。
- <strong>セキュリティモデルとしての分離。</strong> コーディングエージェントには、プッシュ権限のみを持つSSHキーを渡し、チケットトラッカーやソースコード管理プラットフォームへのAPIアクセスは一切与えません。gitだけが外部世界との唯一のインターフェースです。コードベース内に埋め込まれたテキストによってエージェントが操作されたとしても、被害が及ぶ範囲はプッシュされたブランチにとどまり、そのブランチは依然として人間によるレビューを通過しなければなりません。オーケストレーターの認証情報がマシンに触れることは決してなく、作業が終わればマシンは削除されます。
- <strong>CIと一致する開発環境。</strong> RDEセッションは、CIと同じインフラと<GlossTerm baseform="stack">スタック</GlossTerm>上で実行します。これにより、「セッション内でテストが通る」ことと「CIでテストが通る」ことが同じ意味になります。CIが失敗した場合は、失敗したチェックをセッションに伝え、コーディングエージェントが一致する環境内で再現できるようにします。
- <strong>タスクごとに1台のマシン。</strong> 複数のチケットを並行して処理するということは、競合のない複数の分離された環境を持つということです。
- <strong>標準的なツールインターフェース。</strong> セッションの作成、操作、削除は、[RDE MCPサーバー](/bitrise-rde/rde-options/bitrise-rde-mcp-server)上の通常のツール呼び出しにすぎません。Model Context Protocolを話せるAIアシスタントであれば、どれも同じ方法でセッションを操作できるため、独自の統合を構築する必要はありません。

## ベストプラクティス {#best-practices}

このようなエージェントを実際のリポジトリに対して実行する際に、譲れないルールとして扱う価値のあるものをいくつか挙げます。

- <strong>ガードレールはプロンプトではなくコードに組み込む。</strong> システムプロンプトは行動の方向付けはしますが、それを強制するものではありません。どのツールが存在するか、誰のテキストをエージェントが読んでよいか、何に承認が必要かは、プロンプトインジェクションでは回避できないハードチェックにすべきです。
- <strong>ヒヤリハットはすべてガードレールの欠陥として扱う。</strong> エージェントが承認を確認した瞬間に自分自身のプルリクエストをマージしてしまったことがあれば、それ以降はマージに明示的な人間の指示を必須にします。公開リポジトリでは、信頼できない作成者のテキストがモデルに届く前に編集・削除し、外部から見えるすべての書き込みを承認・却下のステップの背後に置きます。
- <strong>重要な2つの意思決定にだけ人間を関与させる。</strong> マージと、外部から見えるものすべてです。計画、コーディング、テスト、レビュアーへの返信は、人間を介さないほうがうまく機能します。
- <strong>「停止」は常に機能するようにする。</strong> 停止コマンドは通常のメッセージキューの外で処理し、実行中のターンの後ろで待たされるのではなく、それを中断できるようにします。
- <strong>フェイルクローズにする。</strong> エージェントが、作成者が信頼できるか、リポジトリが非公開か、チェックが成功したかを確認できない場合は、安全でないほうの答えを前提として処理を保留します。
- <strong>タイピングだけでなく、思考そのものを委任する。</strong> 計画を立てるためであっても、オーケストレーターにソースコードを読ませてはいけません。RDE内で作業ツリー全体を前にしているコーディングエージェントこそが、自らの作業を計画すべきです。タスクにコードの理解が必要になった瞬間、それはRDEの領分です。

## リファレンス実装 {#reference-implementation}

<strong>bitclaw</strong> は、このアーキテクチャのオープンソースのリファレンス実装です。[github.com/bitrise-io/bitclaw-public](https://github.com/bitrise-io/bitclaw-public)。MITライセンスで提供されており、本番環境でそのまま実行するのではなく、学習し適応させることを目的としています。マネージドデータベースの代わりにSQLite、プッシュチャンネルの代わりにポーリング、プレーンなログを使用しています。READMEには、各ガードレールがそれを必要とした障害モードとともに記載されています。

セットアップは段階的になっているため、数分で動作を確認し、そこからコーディングエージェントへと育てていくことができます。

| ティア | 設定するもの | エージェントができること |
|---|---|---|
| 1.&nbsp;チャット | SlackアプリとAnthropicのAPIキー | Slackで@メンションされたときに応答する |
| 2.&nbsp;コード | Bitriseトークン、workspace、RDEテンプレート | リポジトリをクローンし、コードを書き、ブランチをプッシュする |
| 3.&nbsp;出荷 | GitHubトークン、信頼済みのOrg、ウェブフック | プルリクエストを作成し、レビューやCIに反応し、承認が出ればマージする |

ティア1は、3つのenvironment variablesを持つ単一の`docker run`です。

```bash
docker run -it --rm \
  -v bitclaw-data:/data -v bitclaw-claude:/home/app/.claude \
  -p 8080:8080 \
  -e SLACK_BOT_TOKEN=xoxb-your-bot-token \
  -e SLACK_APP_TOKEN=xapp-your-app-token \
  -e ANTHROPIC_API_KEY=sk-ant-your-api-key \
  bitriseio/bitclaw-public:latest
```

ティア2こそが、このリポジトリが存在する理由です。その`docs/rde-template.md`ガイドでは、コーディングエージェント用テンプレート（ウォームアップスクリプトといくつかのsaved inputs）の構築手順を説明しており、これが完成するとボットは実際のコーディング作業をRDEセッションに委任するようになります。

:::caution[独自の脅威モデリングを行ってください]

bitclawのガードレールは実際のインシデントをもとに構築されていますが、それはあくまで参考であり、保証ではありません。自律型エージェントを自分たちのリポジトリに向ける前に、セキュリティモデルを確認し、自分たちの信頼境界に合わせて調整してください。

:::
