このレシピでは、Slackネイティブなコーディングエージェントのアーキテクチャを紹介します。チケットを割り当てるか、スレッドで @メンションするだけで、エージェントが要件を読み取り、計画を投稿し、使い捨ての開発マシンを起動して、コードの作成とテストを行い、プルリクエストを開きます。さらに、レビューコメントやCIの結果が届くたびに対応し、プルリクエストがマージされたら自らクリーンアップします。

中心となる考え方は関心の分離です。小さくロックダウンされたオーケストレーターがSlack上で動作し、コードには一切直接触れません。実際のコーディングはすべて、使い捨ての<GlossTerm baseform="remote dev environment">Remote Dev Environments</GlossTerm>(RDE)に委任します。このアーキテクチャのオープンソースのリファレンス実装である <strong>bitclaw</strong> は、[github.com/bitrise-io/bitclaw-public](https://github.com/bitrise-io/bitclaw-public)で公開されています。詳細については、以下の[リファレンス実装](#reference-implementation)を参照してください。

## エージェントができること {#what-the-agent-does}

Slackでエージェントに送る典型的なリクエストは次のとおりです。

- すでに完全にロールアウトされたフィーチャーフラグを削除する。
- CIが成功するまで、停滞しているプルリクエストを進める。
- 以前のプルリクエストをパターンの参考にして、依存関係をアップグレードする。
- サポートチケットを調査する。
- 監視ツールに表示されるエラーメッセージに、より多くのコンテキストを追加する。

エージェントのユーザーにチケットを割り当てるだけで、作業が始まります。エージェントは共有チャンネルに短い確認メッセージを投稿し、その後はマイルストーンでのみスレッドを更新します。マイルストーンは、計画、開発セッションの作成、コードのプッシュ、プルリクエストのオープン、CIの結果、レビューフィードバックへの対応、マージ、クリーンアップの完了です。途中の細かい手順をすべて報告することはありません。

プルリクエストとチケットはどちらも、それらを所有するスレッドに紐付けられます。そのため、レビューコメント、CIの結果、チケットの遷移が発生するたびにセッションへ伝わります。エージェントはこれらのイベントに自律的に反応します。レビュー担当者のフィードバックに対応し、チケット上のフォローアップの質問に答え、マージが完了すると開発環境を破棄してチケットを遷移させます。

同じループは、より大規模で長期にわたる作業にも対応できます。たとえば、数日にわたり、複数回のマージコンフリクトが発生する複数ファイルのリファクタリングでも、人間に求められるのは定期的なレビューだけです。

## カスタムオーケストレーターを構築する理由 {#why-build-a-custom-orchestrator}

このようなエージェントは、ソースコード、認証情報、チケットトラッカー、そして公開リポジトリではオープンなインターネットなど、機密性の高いものすべてに同時に触れます。汎用の既製エージェントでは、特定のチームにとって信頼できるエージェントにするための要素を実装できません。たとえば、どの作成者の発言を受け付けるか、どの操作に人間の承認が必要か、ワークフローにおける「完了」とは何か、といった要素です。

オーケストレーターを自分で所有すれば、こうしたすべてを自分で管理できるコードとして保持できます。具体的には、エージェントが持つツール、システムプロンプトの指示ではなく実行可能なチェックとして記述された信頼ルール、チームの実際の働き方に合わせたワークフローです。

オーケストレーター自体を大きくする必要はありません。小さな単一のサービスで構成でき、コードを実行せずに中継、計画、ツール呼び出しだけを行うため、後に他のエージェントに対して実行することになる、委任、レビュー、マージのループと同じ流れでコーディングエージェントを使ってブートストラップするのに適しています。

## 基本原則: オーケストレーターはコードを書かない {#core-principle-the-orchestrator-cant-code}

この設計には、1つの重要なルールがあります。<strong>オーケストレーターはコーダーではありません。</strong>

- 1つのSlackスレッドが1つのセッションに対応し、1つの永続的な会話に支えられています。そのため、メッセージ、Webhook、数日後に届くフォローアップの間でコンテキストが失われることはありません。
- すべての機能は、範囲を絞ったツールとして提供されます。Slackへの投稿、プルリクエストの読み取りと管理、チケットトラッカーの読み取り、ログとメトリクスのためのオブザーバビリティツールへのクエリ、RDEセッションの作成と操作です。
- Pull requestsとチケットは、それらを所有するスレッドに紐付けられます。そのため、レビューコメント、CIの結果、チケットの遷移は、適切な会話内のメッセージとして届きます。エージェントはイベントをポーリングで確認するのではなく、イベントに反応します。
- オーケストレーターにはシェルもファイルアクセスもありません。コードを実行できず、チケットトラッカーやソースコントロールのAPIを通じてソースコードを読み取ることもできません。これらのツールは、プロンプトではなくコードで拒否してください。

```
 Ticket assignment ────┐
 Slack @mention ───────┼──► one Slack thread = one session (the orchestrator)
 Webhooks (PR, CI) ────┘        │                          ▲
                                │ creates and drives        │ review, CI, and ticket
                                ▼                           │ events route back
                        RDE session ───── git push ──► pull request
                        (coding agent + full toolchain)
```

## Remote Dev Environments の位置付け {#where-remote-dev-environments-fit}

コーディングエージェントに必要なことはすべて、つまりリポジトリのクローン、パッケージのインストール、ビルドツールやテストスイートの実行、`Makefile`に書かれている内容の実行は、オーケストレーターの認証情報を保持するマシンでは決して実行すべきではありません。代わりに、タスクごとに専用の使い捨てマシンを用意してください。

- <strong>1つのテンプレート、1回のツール呼び出し。</strong> すべてのコーディングマシンを、固定された単一の<GlossTerm baseform="rde template">テンプレート</GlossTerm>から作成します。テンプレートには、スタック、マシンタイプ、そしてコーディングエージェントのインストール、git のみのSSHID のセットアップ、永続的なターミナルセッションでのエージェントの起動を行うウォームアップスクリプトを含めます。認証情報は、<GlossTerm baseform="saved input">保存済み入力</GlossTerm>とセッション入力で渡します。認証情報は暗号化され、イメージに組み込まれることはありません。
- <strong>監視役ではなく、指示書を渡す。</strong> 各セッションは、自己完結したタスク指示書とともに作成します。指示書には、リポジトリ、チケット、受け入れ基準、ブランチのルール、そして1つの行動指示を含めます。その指示とは、入力待ちで停止せず、最も妥当なデフォルトを選び、前提をコミットメッセージとpull request descriptionに記録して、作業を続けることです。誤った前提は、プルリクエストのレビューで修正されます。
- <strong>セキュリティモデルとしての分離。</strong> コーディングエージェントには、プッシュ権限のみを持つSSHキーを渡し、チケットトラッカーやソースコントロールプラットフォームへのAPIアクセスは与えません。外部とのやり取りは git だけです。コードベースに仕込まれたテキストによってエージェントが操作されたとしても、影響範囲はプッシュされたブランチに限られ、そのブランチも人間のレビューを通過する必要があります。オーケストレーターの認証情報がマシンに渡ることはなく、作業が終わればマシンは削除されます。
- <strong>CIと一致する開発環境。</strong> RDEセッションは、CIと同じインフラストラクチャと<GlossTerm baseform="stack">スタック</GlossTerm>で実行します。これにより、「セッション内でテストが成功する」ことと「CIでテストが成功する」ことが同じ主張になります。CIが失敗した場合は、失敗したチェックをセッションに中継し、コーディングエージェントが一致する環境で再現できるようにします。
- <strong>タスクごとに1台のマシン。</strong> 複数のチケットを並行して処理する場合は、競合のない複数の分離された環境を使います。
- <strong>標準的なツールインターフェース。</strong> セッションの作成、操作、削除は、[RDE MCPサーバー](/bitrise-rde/rde-options/bitrise-rde-mcp-server)の通常のツール呼び出しで行います。Model Context Protocol に対応するAIエージェントであれば、同じ方法でセッションを操作できるため、独自の連携を構築する必要はありません。

## ベストプラクティス {#best-practices}

実際のリポジトリに対してこのようなエージェントを実行する場合に、必ず守るべきルールを紹介します。

- <strong>ガードレールはプロンプトではなくコードで実装する。</strong> システムプロンプトは動作を誘導しますが、強制はしません。どのツールが存在するか、エージェントが誰のテキストを読めるか、何に承認が必要かは、プロンプトインジェクションでは回避できないハードチェックにしてください。
- <strong>ヒヤリハットはすべてガードレールの欠陥として扱う。</strong> エージェントが承認を確認した途端に自分のプルリクエストをマージしてしまった場合は、以後、マージには人間による明示的な指示を必須にしてください。公開リポジトリでは、信頼できない作成者のテキストをモデルに到達する前に削除し、外部から見えるすべての書き込みを承認または拒否のステップで制限します。
- <strong>人間は重要な2つの判断に関与する。</strong> マージと、外部から見えるすべての操作です。計画、コーディング、テスト、レビュー担当者への返信は、人間が介在しないほうがうまく機能します。
- <strong>「停止」を常に機能させる。</strong> 停止コマンドは通常のメッセージキューとは別に処理し、実行中のターンの後ろで待たされることなく中断できるようにします。
- <strong>フェイルクローズにする。</strong> 作成者が信頼できるか、リポジトリが非公開か、チェックが成功したかを確認できない場合は、安全でない答えであると想定して処理を保留します。
- <strong>入力作業だけでなく、思考も委任する。</strong> 計画のためであっても、オーケストレーターにソースコードを読ませないでください。RDE 内で完全な作業ツリーを前にしているコーディングエージェントが、自分の作業を計画するべきです。タスクにコードの理解が必要になった時点で、そのタスクは RDE に属します。

## リファレンス実装 {#reference-implementation}

<strong>bitclaw</strong> は、このアーキテクチャのオープンソースのリファレンス実装です: [github.com/bitrise-io/bitclaw-public](https://github.com/bitrise-io/bitclaw-public)。MIT ライセンスで提供されており、本番環境でそのまま実行するのではなく、調べて応用することを想定しています。マネージドデータベースの代わりに SQLite を使い、プッシュチャンネルの代わりにポーリングを使い、ログも簡素なものです。README には、各ガードレールと、それが必要になった障害パターンが併せて記載されています。

セットアップは段階的に進められるため、数分で動作を確認でき、そこからコーディングエージェントへと発展させられます。

| ティア | 設定するもの | エージェントができること |
|---|---|---|
| 1.&nbsp;Chat | Slackアプリと Anthropic APIキー | Slackで@メンションされたときに応答する |
| 2.&nbsp;Code | Bitriseトークン、workspace、RDE テンプレート | リポジトリのクローン、コードの作成、ブランチのプッシュ |
| 3.&nbsp;Ship | GitHubトークン、信頼できる Organization、Webhook | プルリクエストのオープン、レビューとCIへの対応、承認に基づくマージ |

ティア 1 は、3つのenvironment variablesを持つ単一の`docker run`です。

```bash
docker run -it --rm \
  -v bitclaw-data:/data -v bitclaw-claude:/home/app/.claude \
  -p 8080:8080 \
  -e SLACK_BOT_TOKEN=xoxb-your-bot-token \
  -e SLACK_APP_TOKEN=xapp-your-app-token \
  -e ANTHROPIC_API_KEY=sk-ant-your-api-key \
  bitriseio/bitclaw-public:latest
```

ティア 2 がこのリポジトリが存在する理由です。`docs/rde-template.md`ガイドでは、ウォームアップスクリプトと少数の保存済み入力からなるコーディングエージェントのテンプレートの構築手順を説明しています。構築後は、ボットが実際のコーディング作業を RDE セッションに委任します。

:::caution[独自の脅威モデリングを行ってください]

bitclaw のガードレールは実際のインシデントを踏まえて構築されていますが、あくまでリファレンスであり、保証ではありません。自律型エージェントをリポジトリに向ける前に、セキュリティモデルを確認し、自社の信頼境界に合わせて調整してください。

:::
