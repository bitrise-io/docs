<GlossTerm baseform="warm pool">プール</GlossTerm>は、指定した数の<GlossTerm baseform="rde session">RDE セッション</GlossTerm>を起動済みのアイドル状態に保ちます。プールからセッションを作成する場合は、新しいマシンの起動とセットアップの実行に必要な数分ではなく、数秒で済みます。セッションを作成するときと同じように、セッションを一度だけ記述し、保持するウォームセッションの数を設定します。Bitriseはその数のセッションをウォーム状態に保ち、リクエストに応じて 1 つを割り当てます。

プールは以前、warm poolsと呼ばれていました。名前は変わりましたが、識別子は変わっていません。APIは引き続き `/warm-pools` エンドポイントと `warm_pool_id` を使用し、CLIは `--warm-pool` フラグを使用し(`rde warm-pool` も `rde pool` のエイリアスとして引き続き動作します)、MCPツールは `bitrise_devenv_*_warm_pool` という名前を使用します。

次のように、セッションがすぐに必要な場合はプールを使用します。

- 今すぐマシンが必要な AIエージェント。
- 1 日に多数の似たセッションを開始するチーム。
- レビュアーがクリックしてすぐにアプリが画面に表示されることを期待する、[デバイスプレビューリンク](/bitrise-rde/devices/device-preview-links)。

プールは、無料トライアルのworkspacesでは利用できません。

:::warning[アルファ機能]

プールはアルファ版です。RDE UIの <strong>Alpha</strong> バッジがそれを示しています。プールの構成、取得したセッションをパーソナライズする方法、関連するCLIコマンド、MCPツール、APIエンドポイントは、予告なく後方互換性のない形で変更される場合があります。テンプレート、スクリプト、自動化の調整が必要になることを想定してください。

:::

## プールの仕組み {#how-a-pool-works}

プールは、保存済みのセッション構成、ウォームセッションの数、任意の最大セッション数の 3 つの要素で構成されます。プールはworkspaceが所有します。

- 構成には、セッション作成リクエストと同じフィールドが含まれます。<GlossTerm baseform="rde template">テンプレート</GlossTerm>、そのセッション入力値、有効にした機能フラグ、そしてスタック、マシンタイプ、クラスター、仮想デバイスに対する任意の上書き設定です。
- ウォームセッション数は、プールが起動済みで取得可能な状態に保つセッションの数です。Bitriseがセッションを作成し、テンプレートのウォームアップスクリプトと起動スクリプトをそれらのセッションで実行して、準備完了の状態に保ちます。誰かがセッションを取得すると、プールに空きがある間は代わりのセッションが起動します。
- ウォームセッション数が 0 のプールはセッションを保持しませんが、構成のプリセットとしては引き続き機能します。このプールから取得すると、保存済みの構成からセッションが作成されます。
- 最大セッション数は、プールのセッションを同時に使用中にできる数の上限です。デフォルトは <strong>No limit</strong> です。[最大セッション数](#max-sessions)を参照してください。

セッションを取得すると、プールのウォームセッションの 1 つが割り当てられます。Bitriseは、そのセッションの名前を変更し、指定した名前、ラベル、自動終了までの時間を適用します。準備完了のセッションがまだない場合は、まだウォームアップ中のセッションが割り当てられ、起動が完了すると、そのままあなたのセッションになります。プールにウォームセッションがまったくない場合は、代わりにBitriseがプールの構成からセッションを作成します。すべてのセッションには作成元が記録されます。取得したセッションのウォーム状態は `claimed`、オンデマンドで作成したセッションのウォーム状態は `cold` です。RDE UIのセッション一覧では、これらが <strong>Claimed</strong> バッジと <strong>Built cold</strong> バッジとして表示されます。

ウォームセッションは、取得されるのを待っている通常のセッションであり、待機中もマシン時間のコストがかかります。誰かが取得するまでは、どのセッション一覧にも表示されず、誰も接続、変更、終了できません。セットアップスクリプトが正しく動作するかどうかは、プールページでログを確認できます。ウォームセッションには自動終了タイマーがありません。誰かが取得するか、プールの縮小や構成の変更によりBitriseがそのセッションを破棄するまで、待機し続けます。

## プールを使用できるユーザー {#who-can-use-a-pool}

RDE にアクセスできる <GlossTerm baseform="workspace">workspace</GlossTerm>のすべてのメンバーが、プールを表示し、プールからセッションを取得し、プールを管理できます。[Workspace API トークン](/bitrise-platform/workspaces/workspace-api-token)を使うと、CI からプールにアクセスできます。

プールの入力値は通常の値として保存され、シークレットとしてマークした場合は保存時に暗号化されます。[保存済みの入力値](/bitrise-rde/configuration/saved-inputs)は個人のものであるため、プールから参照できません。プールが使用できる保存済み入力値を持つ、特定の個人がいないためです。

## 取得したセッションの所有者 {#who-owns-a-claimed-session}

プールから取得したセッションは、自分で作成したセッションと同様にあなたのものであり、自分だけが表示と管理を行えます。ウォームセッションは誰かが取得する前に起動されているため、保存済みの入力値や GitHub の認証情報など、個人に紐づくものは含まれていません。これらは、取得後に追加してください。たとえば SSH 経由で追加できます。

取得したセッションを共有したい場合は、取得時に所有者として <strong>Workspace</strong> を選択します。すると、すべてのメンバーが <strong>Workspace sessions</strong> の下でそのセッションを表示、管理できるようになり、作成者としてあなたが記録されます。Workspace API トークンで取得したセッションや、[プレビューリンク](/bitrise-rde/devices/device-preview-links)から開かれるデバイスセッションは、常に workspace に属します。

## プールの作成 {#creating-a-pool}

<Tabs>
<TabItem value="ui" label="RDE UI" default>

1. Remote Dev Environmentsセクションで <strong>Pools</strong> を開き、<strong>New pool</strong> をクリックします。テンプレートのページから <strong>Create pool</strong> をクリックすると、そのテンプレートが選択済みの同じフォームが開きます。
1. テンプレートを選択します。フォームには、そのテンプレートに必要な項目だけが表示されます。セッション入力値、機能フラグ、テンプレートがデバイスを起動する場合はデバイスのセクション、そしてセッションフォームと同じ <strong>Override machine configuration</strong> スイッチです。
1. <strong>Pool name</strong> を入力します。
1. <strong>Warm sessions</strong> を設定し、プールに上限を設ける場合は <strong>Max sessions</strong> を設定します。上限を設けない場合は、<strong>Max sessions</strong> を空のままにします。
1. <strong>Create pool</strong> をクリックします。

プールページには、準備完了のセッション数と、まだウォームアップ中のセッション数が表示されます。また、ウォームセッションが名前の一覧で表示され、取得されたセッションとコールドセッションの累計数も確認できます。

</TabItem>
<TabItem value="cli" label="CLI">

```bash
bitrise-cli rde pool create ios-reviewers --template "iOS Xcode 26" --size 2 --max-sessions 20
```

`--input` と `--secret-input` はテンプレートのセッション入力値を設定し、`--feature-flag` はテンプレートの機能フラグを有効にします。`--stack`、`--machine-type`、`--device-*` フラグは、テンプレートで宣言された内容を上書きします。`--size` はウォームセッションの数、`--max-sessions` はプールの上限です。上限を設けない場合は、最大セッション数を指定しません。プール ID を受け取るコマンドは、すべてプールの名前も指定できます。

</TabItem>
<TabItem value="mcp" label="AI agent (MCP)">

たとえば、次のように自然な言葉で依頼します。*「チーム用に、iOS Xcode 26 テンプレートのセッションを 2 つウォーム状態に保ち、使用中は 20 を超えないようにしてください。」* エージェントは、テンプレート、入力値、`warm_sessions`、`max_sessions` を指定して `bitrise_devenv_create_warm_pool` を呼び出します。

</TabItem>
<TabItem value="api" label="API">

```bash
curl -X POST "https://api.bitrise.io/rde/v1/workspaces/WORKSPACE_ID/warm-pools" \
  -H "Authorization: token YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "ios-reviewers",
    "template_id": "TEMPLATE_ID",
    "warm_sessions": 2,
    "max_sessions": 20
  }'
```

構成フィールドは、セッション作成リクエストと同じです。`warm_sessions` は以前 `pool_size` と呼ばれていました。古い名前は 1 リリースの間、引き続き受け付けられて返され、その後削除されます。APIリファレンスの[プールの作成](/bitrise-rde-api/api-reference/codespaces-service-create-warm-pool)を参照してください。

</TabItem>
</Tabs>

Bitriseは、セッション作成リクエストと同じ方法で構成を検証します。不明な入力値、必須入力値の欠落、マシンタイプで実行できないデバイスは、保存時に拒否されます。ウォームセッションは、他のセッションと同様にworkspaceの CPU を使用します。workspaceの CPU が不足していてプールが目標数に達しない場合、プールページにエラーが表示され、プールは再試行を続けます。

## セッションの取得 {#claiming-a-session}

<Tabs>
<TabItem value="ui" label="RDE UI" default>

<strong>New session</strong> フォームでテンプレートを選択すると、<strong>Start from pool</strong> にそのテンプレートのプールが一覧表示され、プールが 1 つだけの場合は自動的に選択されます。プールを選択すると、プールが構成のセクションを固定します。セッションの名前、所有者(デフォルトは <strong>Me</strong>)、自動終了までの時間だけを指定します。プールのページにも <strong>Claim a session</strong> ボタンがあり、そのプールが選択済みのフォームが開きます。

</TabItem>
<TabItem value="cli" label="CLI">

```bash
bitrise-cli rde session create my-fix --warm-pool ios-reviewers
```

</TabItem>
<TabItem value="mcp" label="AI agent (MCP)">

エージェントは `warm_pool_id` を `bitrise_devenv_create` に渡します。取得できるプールを確認するには、`bitrise_devenv_list_warm_pools` を呼び出します。

</TabItem>
<TabItem value="api" label="API">

セッション作成リクエストで `warm_pool_id` を設定し、構成フィールドは空のままにします。

</TabItem>
</Tabs>

プールが構成を固定します。テンプレート、入力値、機能フラグ、スタック、マシンタイプ、クラスター、デバイスのいずれかも指定した取得リクエストは、無視されるのではなく拒否されます。セッションごとに、名前、説明、ラベル、自動終了までの時間は引き続き指定できます。デバイスを起動するプールの場合は、インストールするアプリのビルドも選択できます。

## 最大セッション数 {#max-sessions}

<strong>Max sessions</strong> は、プールのセッションを同時に使用中にできる最大数です。取得したセッションとコールドで作成したセッションが対象で、プールのウォームセッションも数に含まれます。デフォルトは <strong>No limit</strong> で、上記で説明した動作そのものです。

複数のグループがworkspaceの CPU を共有していて、1 つのグループにすべてを使わせたくない場合に、最大セッション数を設定します。たとえば、タスクごとにセッションを開くエージェント群や、[デバイスプレビューリンク](/bitrise-rde/devices/device-preview-links)が対応するレビュアーなどです。プールのマシンタイプは 1 つなので、vCPU 6 個のマシンタイプで最大 10 セッションを設定すると、そのグループの上限は 60 vCPU になります。

プールの作成時に設定するか、後からプールのページで <strong>Change limits</strong> を使って、`bitrise-cli rde pool update --max-sessions` で、`bitrise_devenv_update_warm_pool` で、または[プールの更新](/bitrise-rde-api/api-reference/codespaces-service-update-warm-pool)リクエストの `max_sessions` で設定できます。ウォームセッション数や最大セッション数を変更するには、workspaceの使用状況を表示する権限が必要です。Workspace APIトークンには常にその権限があります。上限を変更しても、ウォームセッションには影響しません。

上限の仕組みは次のとおりです。

- <strong>予約ではなく上限です。</strong> 最大セッション数は、プールがそれ以上使用することを防ぎます。アイドル状態のプールのために何かを確保することはなく、すべてのプールの最大セッション数を合計すると、workspaceの CPU クォータを超える場合があります。最大セッション数に達していないプールでも、workspaceの CPU が不足していると拒否されることがあります。
- <strong>使用中</strong>とは、セッションのマシンが起動中、実行中、終了中、またはドレイン中であることを指します。<strong>Usage</strong>ページがカウントするものと同じです。終了したセッションは、枠を解放します。
- <strong>ウォームセッションは、最大セッション数が残した空きを埋めます。</strong> 最大セッション数に達している状態でウォームセッションを取得することは常に成功します。拒否されるのは、ウォームセッションが見つからない取得です。ウォームセッション数は、最大セッション数を超えることはできません。
- <strong>復元もカウントされます。</strong> 終了したセッションの復元や、失敗したセッションの起動は、再びプールの枠を使用します。プールが満杯の場合、復元は拒否され、セッションは終了したまま、そのままの状態で残ります。
- <strong>Full</strong> は、使用中のセッションが最大セッション数に達したときにプールが表示する状態です。<strong>Over max</strong> は、使用中の数を下回るように最大セッション数を下げた後に表示される状態です。セッションは終了されず、十分な数のセッションが終了するまで取得は拒否されます。プールのページ、プールの一覧、<strong>Usage</strong>ページ、`bitrise-cli rde pool list`、APIの `status.limit_state` のすべてに、この状態が表示されます。
- プールのページの <strong>Refused (last 7 days)</strong> は、プールが満杯だったために拒否された取得と復元の数をカウントします。この数が増え続ける場合は、需要に対して最大セッション数が低すぎます。

### 取得が拒否された場合 {#when-a-claim-is-refused}

拒否の際は、常に何が起きたのかが示されます。そのプールで使用中のあなた自身のセッションが一覧表示されるか、あなたのセッションがないことが示され、次に行うことも示されます。自分のセッションを使う、不要なセッションを終了する、またはプールのセッションが終了するまで待ってから再試行する、のいずれかです。workspaceの管理者は、プールの最大セッション数を引き上げることができます。拒否の際に、プール外のセッションが提案されることはありません。

APIは、HTTP `429` と、次の 2 つの理由のいずれかで応答します。理由は `google.rpc.ErrorInfo` の詳細と、数値、あなたのセッション、次の手順を含む `codespaces.v1.WarmPoolRefusal` の詳細で伝えられます。

| 理由 | 発生する場合 |
|---|---|
| `POOL_FULL` | プールの使用中のセッションが最大セッション数に達していて、取得でウォームセッションが見つからなかったか、復元または起動で枠が必要な場合。 |
| `CPU_QUOTA_EXHAUSTED` | セッションのマシンファミリーに対して、workspaceの CPU が不足している場合。プールには最大セッション数までの空きがありますが、workspace全体が満杯です。プールなしで作成されたセッションでも返されます。 |

RDE UIでは、満杯のプールを選択した時点で <strong>New session</strong> フォームに、復元が拒否された場合はセッションのページに、拒否の内容が表示されます。CLIとMCPツールは、プールにあるあなたのセッションとともにテキストとして出力するため、人間でもエージェントでも同じ内容を読み取れます。

## プールを正常に保つ {#keeping-the-pool-healthy}

Bitriseはすべてのプールを定期的にチェックし、最大セッション数が残した空きの範囲で、ウォームセッションを設定した数に保ちます。次の点に注意してください。

- <strong>構成を編集すると、ウォームセッションが置き換えられます。</strong> 入力値、機能フラグ、マシンまたはデバイスの設定を変更すると、Bitriseは古い構成でウォームアップしたセッションを破棄し、新しいセッションを起動します。UIは、そのような変更を保存する前に警告します。プールの名前の変更や上限の変更は、ウォームセッションに影響しません。
- <strong>テンプレートの編集でも同じことが起こります。</strong> プールはテンプレートに従うため、テンプレートのスクリプトや変数を編集すると、プールのウォームセッションも置き換えられます。
- <strong>構成が壊れると、プールは一時停止します。</strong> テンプレートの編集によって、プールが設定していない必須入力値が追加されたり、プールが有効にしている機能フラグが削除されたりする場合があります。この場合、プールは構成エラーを表示し、修正するまでセッションの作成を停止します。プールの既存のウォームセッションは、引き続き取得できます。
- <strong>失敗が繰り返されると、プールは一時停止します。</strong> プールは再試行までしばらく待機するため、壊れたセットアップスクリプトが新しいマシンを起動し続けることはありません。最後のエラーは、プールのページに表示されます。

## スケジュールによるプールのスケーリング {#scaling-a-pool-on-a-schedule}

ウォームセッションは、アイドル中もマシン時間のコストがかかるため、その数は需要に必要な分だけに保ってください。数の変更は 1 回の呼び出しで済むため、スケジュール運用も簡単です。業務時間に向けてプールをウォームアップし、夕方に空にします。Workspace APIトークンを使った cron ジョブで実行できます。

```bash
0 8  * * 1-5  BITRISE_TOKEN=bitwat_… bitrise-cli rde pool set-size ios-reviewers 3 --workspace WORKSPACE_ID -q
0 19 * * 1-5  BITRISE_TOKEN=bitwat_… bitrise-cli rde pool set-size ios-reviewers 0 --workspace WORKSPACE_ID -q
```

ウォームセッション数を 0 にすると、すべてのウォームセッションが破棄されますが、プール、その構成、およびそのプールで発行されたプレビューリンクは残ります。プールを削除すると、そのウォームセッションが破棄され、プレビューリンクも無効になります。すでにプールから取得したセッションは通常のセッションであり、どちらの操作も影響しません。

## デバイスプールとプレビューリンク {#device-pools-and-preview-links}

プールのテンプレートが仮想デバイスを起動する場合、プールはデバイスも起動済みの状態に保ちます。このため、[デバイスプレビューリンク](/bitrise-rde/devices/device-preview-links)は、アプリのダウンロードにかかる時間で開きます。プールを指定してリンクを発行すると、リンクが開かれるたびに、そのウォームデバイスの 1 つが取得されます。[プールからのリンクの提供](/bitrise-rde/devices/device-preview-links#serving-links-from-a-pool)を参照してください。

デバイスプールからの取得では、アプリのビルドをすぐにインストールできます。ビルドの URL をセッションのアーティファクトとして渡します。デバイスはすでに実行されているため、セッションが割り当てられた時点でアプリがインストールされます。

## プールの管理 {#managing-pools}

<strong>Pools</strong>ページには、workspaceのプールが、最大セッション数に対する使用中のセッション数とともに一覧表示され、該当する場合は <strong>Full</strong> または <strong>Over max</strong> のバッジが表示されます。プールのページでは、上限の変更、構成の編集、セッションの取得、プールの削除を行えます。CLIは `bitrise-cli rde pool list`、`view`、`update`、`set-size`、`delete` で同じ操作を行え、[API](/bitrise-rde/configuration/rde-api#pools)ではプールのエンドポイントで行えます。

Workspaceのオーナーと、請求を管理するメンバーは、すべてのプール、そのウォームセッション、最大セッション数に対する使用中のセッション数も確認できます。プールは <strong>Usage</strong> ページと `bitrise-cli rde pool list --all` に、workspaceのその他の RDE 支出とともに表示されます。
