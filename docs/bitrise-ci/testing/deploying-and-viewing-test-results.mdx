View your test results in one place after a Bitrise CI build. All tests will be available on the build page, even if you have multiple testing <GlossTerm baseform="step">Steps</GlossTerm> in your <GlossTerm baseform="workflow">Workflows</GlossTerm>. Our goal is to make sure you have accessible and `actionable` test results on Bitrise, leading to faster time to recover from test failures and a better overall developer experience.


## Deploying test results

Deploy your test results on the build page with minimal configuration. The requirements depend on your setup:

- Using the official Bitrise testing Steps to run tests
- Using other Steps to run tests

### Deploying results from the official Bitrise testing Steps

The supported testing Steps are the following:

- **Android Unit Test**: [Android unit tests](/bitrise-ci/testing/testing-android-apps/android-unit-tests).
- **Android Instrumented Test**: [Running instrumented tests for Android apps](/bitrise-ci/testing/testing-android-apps/running-instrumented-tests-for-android-apps).
- **Xcode Test for iOS**: [Running unit and UI tests for iOS apps](/bitrise-ci/testing/testing-ios-apps/running-unit-and-ui-tests-for-ios-apps).
- **iOS Device Testing**: [Device testing for iOS](/bitrise-ci/testing/device-testing-with-firebase/device-testing-for-ios).
- **Virtual Device Testing for Android**: [Device testing for Android](/bitrise-ci/testing/device-testing-with-firebase/device-testing-for-android).
- **Flutter Test**: [Testing Flutter apps](/bitrise-ci/testing/testing-flutter-apps/running-the-dart-analyzer-on-bitrise).

If you use any of these Steps, make sure you have the **Deploy to Bitrise.io** Step in your Workflow. Bitrise will automatically deploy your test results to the build page.

:::important[Attachments and flaky tests]

If your tests generate attachments or you want Bitrise to show flaky tests, the **Deploy to Bitrise.io** Step must be of version 2.19.1 or newer.

:::

### Deploying results from other Steps

If you run your tests using other Steps (for example, you can use [Script](https://bitrise.io/integrations/steps/script) Steps for a fully custom testing solution), you need some additional configuration.

1. Add the Step running your tests to your Workflow.
1. Add the **Export test results to the Test Reports** Step to your Workflow.
1. Configure the Step: [Using the Export test results to the Test Reports Step](/bitrise-ci/testing/deploying-and-viewing-test-results#using-the-export-test-results-to-test-reports-step).
1. Make sure you have the **Deploy to Bitrise.io** Step in your Workflow.

   :::important[Attachments and flaky tests]

   If your tests generate attachments or you want Bitrise to show flaky tests, the **Deploy to Bitrise.io** Step must be of version 2.19.1 or newer. To link attachments by file name, it must be version 2.26.0 or newer: [Naming attachments after their test case](/bitrise-ci/testing/deploying-and-viewing-test-results#naming-attachments-after-their-test-case).

   :::


## Viewing test results

:::note[Rich HTML reporting]

If you use [rich HTML test reports](/bitrise-ci/testing/testing-ios-apps/viewing-xcode-test-results-in-rich-html-format), you can still find those on the **Artifacts** tab.

:::

To view your results, open the build page and select the **Tests** tab. Your tests are sorted into different tabs based on their status:

- Failed
- Passed
- Skipped
- Error
- Flaky

By default, Bitrise shows the list of failed tests. You can view test run details within each of these categories.

Click any test to check the details: the duration of the test, the output, and any attachments that the test generated. For easier debugging of failures, test reports display attached image files in line with their associated test cases.

:::note[Supported file formats]

Currently, we support the following file formats for attachments:

`.jpg, .jpeg, .png, .txt, .log, .mp4, .webm, .ogg`

:::

You can view flaky tests on the **Flaky** tab. Flaky tests are tests that sometimes fail and sometimes succeed without any changes in the code. If a test fails and then succeeds on [an automatic retry](/bitrise-ci/testing/testing-ios-apps/running-unit-and-ui-tests-for-ios-apps#test-repetitions), Bitrise marks the test as flaky, and you can view it on the **Flaky** tab. It also displays the details and attachments for each retry of the test. You can find more information on how to detect flaky tests and how to quarantine them, if needed, in [Detecting and quarantining flaky tests](/bitrise-ci/testing/detecting-and-quarantining-flaky-tests).

![test-run.png](/img/_paligo/uuid-53eba539-6b4d-b4cf-c33d-6168fca79640.png)

Test reports also support the use of the `system-out` tag in JUnit. If a test case includes this tag, we display its contents on the **Test output** tab. If a test case has both a `system-out` tag and produces an error message, we display both.


## Collating test attachments with test results

Many tests generate image files (screenshot tests, XCUITests, etc). Bitrise test reports automatically collate image files with associated test cases for Xcode tests (using the `xcresult` file).

:::note[Supported file formats]

Currently, we support the following file formats for attachments:

`.jpg, .jpeg, .png, .txt, .log, .mp4, .webm, .ogg`

:::

If your tests don't generate an `xcresult` file, Bitrise can still show attachments under their test cases. There are two ways to link them:

- Name each file after its test case: [Naming attachments after their test case](#naming-attachments-after-their-test-case).
- Reference each file in the JUnit XML: [Referencing attachments in the JUnit XML](#referencing-attachments-in-the-junit-xml).

### Naming attachments after their test case

Name a screenshot, recording, or log after the test case that produced it, and Bitrise shows it under that test on the **Tests** tab. You don't have to edit the JUnit XML or write a script that links the files.

:::important[Step versions]

Linking attachments by file name requires the **Deploy to Bitrise.io** Step version 2.26.0 or newer. If you export your test results with the **Export test results to Test Reports** Step, it must be version 1.3.0 or newer.

:::

The file name has the following structure:

```text
<classname>__<name>[__run<k>]__<label>.<ext>
```

For example:

```text
com.example.LoginTest__emptyState__1.png
com.example.LoginTest__wrongPassword__run2__api34.png
com.example.LoginTest__wrongPassword__locked__1.png
```

The third file belongs to the test called `wrongPassword__locked`.

| Part | Rule |
|---|---|
| `classname`, `name` | The `classname` and `name` attributes of the `<testcase>` element in your JUnit XML, case-sensitive. Replace each of the `" * / : < > ? \ \|` characters with `_`. |
| `run<k>` | Optional. `k` is one or higher, and selects the k-th occurrence of the test case in its test suite: the **Run #k** card on the **Tests** tab. Without it, the file goes to the first run. |
| `label` | Required. Any text that doesn't contain `__` and doesn't start with `_`: a counter (`1`), a device (`api34`), or both (`api34_1`). Attachments are sorted by label, with numbers in numeric order, so `2` comes before `10`. |
| `ext` | One of `png`, `jpg`, `jpeg`, `mp4`, `webm`, `ogg`, `txt`, `log`, in any case. |

Keep the following in mind:

- Only the file name counts for matching, not the folder. The file still has to be somewhere the Steps look for it: [Exporting the attachments](#exporting-the-attachments).
- A test name can contain `__`. If a test's own name ends in `__run<k>`, the file goes to that test, not to a run of another test.
- When the same tests run more than once in a build, for example on two emulators, put the device in the label, such as the API level. Otherwise, the files overwrite each other or get skipped as copies.
- If the same test case appears in more than one test suite of a report, its files aren't linked, because Bitrise can't tell which test case they belong to.
- Attachment problems never fail the build. To find out why a file isn't linked, see [Troubleshooting missing attachments](#troubleshooting-missing-attachments).

A file name can be at most 255 bytes on Linux and Android, and 255 characters on macOS. Long test names, such as parameterized tests or Kotlin test names written in backticks, can exceed this limit together with the label and the extension. Saving the file then fails in your own test code (`ENAMETOOLONG`). Bitrise doesn't shorten the names.

#### Saving attachments from your test tool

Set up the naming once, in your test configuration, so that you don't have to change your tests. Build the name from the same `classname` and `name` values that your JUnit reporter writes into the XML, replace the characters listed above, and always add a label. The following examples do this for some popular test tools.

<Tabs>
<TabItem value="android" label="Android" default>

**AndroidX Test and Espresso**

Register a JUnit `RunListener` once, through an instrumentation runner argument. Before each test, the listener installs an Espresso failure handler that takes a screenshot when an Espresso check fails, and saves it to test storage. The Android Gradle plugin then pulls the screenshot into `build/outputs/connected_android_test_additional_output/`.

```kotlin
// app/build.gradle.kts
android {
    defaultConfig {
        testInstrumentationRunnerArguments["listener"] = "com.example.testing.BitriseScreenshotListener"
        testInstrumentationRunnerArguments["useTestStorageService"] = "true"
    }
}

dependencies {
    androidTestUtil("androidx.test.services:test-services:1.6.0")
}
```

```kotlin
// app/src/androidTest/java/com/example/testing/BitriseScreenshotListener.kt
package com.example.testing

import android.os.Build
import androidx.test.core.app.takeScreenshot
import androidx.test.core.graphics.writeToTestStorage
import androidx.test.espresso.Espresso
import androidx.test.espresso.base.DefaultFailureHandler
import androidx.test.platform.app.InstrumentationRegistry
import org.junit.runner.Description
import org.junit.runner.notification.RunListener

private fun clean(value: String) = value.replace(Regex("""["*/:<>?\\|]"""), "_")

class BitriseScreenshotListener : RunListener() {
    override fun testStarted(test: Description) {
        val default = DefaultFailureHandler(InstrumentationRegistry.getInstrumentation().targetContext)
        Espresso.setFailureHandler { error, viewMatcher ->
            val name = "${clean(test.className)}__${clean(test.methodName)}__api${Build.VERSION.SDK_INT}_failure"
            takeScreenshot().writeToTestStorage(name)
            default.handle(error, viewMatcher)
        }
    }
}
```

Only failed Espresso checks get a screenshot, not plain JUnit assertions. The API level in the label keeps the screenshots of devices with different API levels apart.

**Roborazzi**

Add a task that copies Roborazzi's screenshots under the attachment name after each Roborazzi run. Roborazzi names its files `<class>.<method>.png`, so the task can rename them without any change to your tests:

```kotlin
// app/build.gradle.kts
val bitriseScreenshots by tasks.registering(Sync::class) {
    from(layout.buildDirectory.dir("outputs/roborazzi")) { include("*.png") }
    into(layout.buildDirectory.dir("bitrise-screenshots"))
    rename("""(.+)\.([^.]+?)(?:_(\d+))?(_actual|_compare)?\.png""", "$1__$2__screenshot$3$4.png")
}
tasks.named { it == "finalizeTestRoborazziDebug" }.configureEach { finalizedBy(bitriseScreenshots) }
```

Roborazzi only writes screenshots when you run `recordRoborazziDebug`, `verifyRoborazziDebug`, or `compareRoborazziDebug`. Parameterized tests don't get attachments, because Roborazzi doesn't put the parameters in the file name.

</TabItem>
<TabItem value="react-native" label="React Native">

**Detox**

Detox names every per-test artifact, such as screenshots, videos, and logs, through a path builder. With its default templates, jest-junit writes the describe blocks and the test title into both `classname` and `name`, so the path builder can rebuild them from the test's title and full name. Point `artifacts.pathBuilder` in your Detox configuration to this file:

```javascript
// e2e/bitrisePathBuilder.js
const path = require('path');

const clean = (value) => value.replace(/["*/:<>?\\|]/g, '_');

module.exports = class BitrisePathBuilder {
  constructor({ rootDir }) {
    this.rootDir = rootDir;
  }

  buildPathForTestArtifact(artifactName, testSummary) {
    if (!testSummary) return path.join(this.rootDir, artifactName);

    const { title, fullName } = testSummary;
    const key = clean(`${fullName.slice(0, -title.length).trim()} ${title}`);
    const ext = path.extname(artifactName);
    const label = path.basename(artifactName, ext).replace(/_+/g, '_').replace(/^_/, '');
    return path.join(this.rootDir, `${key}__${key}__${label}${ext}`);
  }
};
```

Because the full test name appears twice, long test names reach the file name length limit sooner.

</TabItem>
<TabItem value="web" label="Web">

**Playwright**

Add a reporter that copies the screenshots and videos Playwright attaches to a test under the attachment name. The junit reporter writes the spec file as `classname`, and the describe blocks and the test title as `name`. Turn on `includeProjectInTestName`, so that each project writes its own test case. Without it, every project writes the same test case, and none of them gets attachments:

```typescript
// playwright.config.ts
reporter: [
  ['junit', { outputFile: 'test-results/junit.xml', includeProjectInTestName: true }],
  ['./bitrise-reporter.ts'],
],
use: { screenshot: 'only-on-failure', video: 'retain-on-failure' },
```

```typescript
// bitrise-reporter.ts
import fs from 'node:fs';
import path from 'node:path';
import type { Reporter, TestCase, TestResult } from '@playwright/test/reporter';

const clean = (value: string) => value.replace(/["*/:<>?\\|]/g, '_');
const supported = /\.(png|jpe?g|mp4|webm|ogg|txt|log)$/i;

export default class BitriseAttachments implements Reporter {
  onTestEnd(test: TestCase, result: TestResult) {
    const [, project, file, ...titles] = test.titlePath();
    const key = `${clean(file)}__${clean((project ? `[${project}] ` : '') + titles.join(' › '))}`;
    const files = result.attachments.filter((a) => a.path && supported.test(a.path));
    files.forEach((a, i) => {
      const label = (result.retry ? `retry${result.retry}_` : '') + (i + 1);
      const target = path.join('test-attachments', `${key}__${label}${path.extname(a.path!)}`);
      fs.mkdirSync(path.dirname(target), { recursive: true });
      fs.copyFileSync(a.path!, target);
    });
  }
}
```

A retried test stays one test case in the XML, so the reporter puts the retry in the label instead of using `run<k>`.

#### Exporting the attachments

If you run your tests with a Script Step or another Step that doesn't export its own results, the **Export test results to Test Reports** Step exports the attachments together with the JUnit XML.

<Tabs>
<TabItem value="workflow-editor" label="Workflow Editor" default>

1. <Partial_OpeningTheWorkflowEditor />
1. Add the **Export test results to Test Reports** Step to your Workflow after the Step that runs your tests.
1. In the **Test result base path** input, set a folder that contains both your test results and your attachments, for example `app/build/`.

   The Step looks for attachments only in this folder. If it points to the folder of the XML, for example `app/build/test-results/`, the Step doesn't find screenshots saved elsewhere.
1. In the **Test result search pattern** input, set a pattern that matches a single JUnit XML, for example `*/test-results/testDemoDebugUnitTest/TEST-com.example.ScreenshotTest.xml`.

   The Step exports only the first match. A wider base path makes it more likely that the pattern matches more than one file. Gradle writes a separate XML for each test class, so only the tests and attachments of the matched class show up.
1. Make sure you have the **Deploy to Bitrise.io** Step at the end of your Workflow.

</TabItem>
<TabItem value="configuration-yaml" label="Configuration YAML">

1. Add the `custom-test-results-export` Step to your Workflow after the Step that runs your tests.
1. Set `base_path` to a folder that contains both your test results and your attachments, and set `search_pattern` to a pattern that matches a single JUnit XML.

   The Step looks for attachments only in `base_path`, and exports only the first match of `search_pattern`. Gradle writes a separate XML for each test class, so only the tests and attachments of the matched class show up.
1. Add the `deploy-to-bitrise-io` Step to the end of your Workflow.

   ```yaml
   workflows:
     screenshot-tests:
       steps:
       - script@1:
           inputs:
           - content: ./gradlew testDebugUnitTest
       - custom-test-results-export@1:
           inputs:
           - test_name: screenshot_tests
           - base_path: app/build/
           - search_pattern: "*/test-results/testDebugUnitTest/TEST-com.example.ScreenshotTest.xml"
       - deploy-to-bitrise-io@2: {}
   ```

</TabItem>
</Tabs>

After exporting the XML, the Step copies every file whose name matches a test case in that XML into the report. It skips the following files:

- Files tracked by git, such as committed reference images
- Files in dependency and tool folders, such as `.git`, `node_modules`, `Pods`, and `.dart_tool`
- Files that an earlier Step already exported

Outside a git repository, the Step logs a warning and doesn't filter out committed files.

If you copy the files into the report folder yourself, for example with a Script Step, the **Deploy to Bitrise.io** Step links them by name, too.

#### Troubleshooting missing attachments

The Steps report attachment problems in the build log:

- If a file name doesn't match any test case, for example because of a typo or a missing label, the **Export test results to Test Reports** Step skips the file without a warning. To see which files it skipped and why, set its **Enable verbose logging?** input to `yes`.
- If the **Export test results to Test Reports** Step finds a matching file but can't link it, for example because more than one file has the same name, it logs `Skipping attachment <file>: <reason>`.
- If the **Deploy to Bitrise.io** Step can't link a file in the report folder, it logs `Test attachment <file> is not linked to a test case: <reason>`.
- Use a lowercase `.xml` extension for your JUnit XML. Bitrise doesn't recognize test results with an uppercase `.XML` extension.
- The **Export test results to Test Reports** Step exports `.junit` test results without attachments.
- Bitrise drops `attachment_*` properties on a `<testsuite>` element. Add them to the `<testcase>` element instead.

### Referencing attachments in the JUnit XML

If you can't name the files after their test cases, reference them in the JUnit XML instead:

<Tabs>
<TabItem value="workflow-editor" label="Workflow Editor" default>

1. Generate a `JUnit.xml` file from your tests.

   The general file structure should look something like this:

   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <testsuites time="15.682687">
       <testsuite name="Tests.Registration" time="6.605871">
           <testcase name="testCase1" classname="Tests.Registration" time="2.113871" />
       </testsuite>
   </testsuites>
   ```
1. Add a `<properties>` element to associate an attachment with a `testcase`.

   The `name` attribute of the element must be set with a value `attachment_#` where `#` is the ordered index of the attachment file, and the value is the filename. Bitrise will show attachments for any test with the attachment properties, but it's most common to only attach screenshots to failed tests. Mark a test as failed with a `<failure>` element.

   ```xml
   <testcase name="testCase1" classname="Tests.Registration" time="2.113871" />
     <failure message="Assertion error message" type="AssertionError">
       Call stack printed here
     </failure>
     <properties>
       <property name="attachment_1" value="pp1.jpg" />
       <property name="attachment_2" value="pp2.jpg" />
     </properties>            
   </testcase>
   ```
1. Add the **Export test results to Test Reports** Step to your Bitrise Workflow. It should be version 1.1.0 or higher.
1. Set a test name in the **The name of the test** input.
1. Set the path to your JUnit XML file in the **Test result search pattern** input.
1. Add the **Deploy to Bitrise.io** Step to the end of your Workflow.

   You don't have to change the default input values.

## Using the Export test results to Test Reports Step

You can use the **Export test results to Test Reports** Step to make sure your test results appear on the **Tests** tab, even if you use Steps that don’t automatically export their results.

With the correct configuration, the Step finds the test results in your project’s repository and puts them in the export directory.

1. <Partial_OpeningTheWorkflowEditor />
1. Add the **Export test results to Test Reports** Step to your Workflow after the Step that runs your tests.
1. In the **The name of the test** input, set the name of the test run.
1. In the **Test result base path** input, set the path where your test results can be found.

   ![Managing_an_app_s_bitrise.png](/img/_paligo/uuid-fd13332e-571f-e706-88ed-a20a29db7aea.png)

   We recommend setting a folder here, though you can also set a specific filepath. The default value is the source directory of your project. Example patterns:

   - If your project’s root directory is `app`: `app/build/test-results/testDemoDebugUnitTest/`
   - If your test results are within a project folder but `app` is not the root directory: ./app/build/test-results/testDemoDebugUnitTest/

   The Step also looks for [attachments named after their test case](/bitrise-ci/testing/deploying-and-viewing-test-results#naming-attachments-after-their-test-case) in this folder. If your tests save attachments, such as screenshots, outside this folder, set a folder that contains both, for example `app/build/`. Then make the search pattern in the next input specific enough to match a single test result.
1. In the **Test result search pattern** input, set a pattern that matches your test result file.

   This search pattern is used to search every file and folder of the path that was set in the **Path where custom test results reside** input.

   If there is more than one match, the Step will export the first match with a warning in the logs. If you set a specific filepath in the previous input, just set * here.

   Example patterns:

   - Matching all files within the base path: `*`
   - Matching all files within a given directory of the base path: `*/build/test-results/testDemoDebugUnitTest/*`
   - Matching a single JUnit XML when the base path is a wider folder, such as `app/build/`: `*/test-results/testDemoDebugUnitTest/TEST-com.example.ScreenshotTest.xml`
1. In the **Step’s test result directory** input, make sure the path is correct.

   Do NOT modify this input’s value: this is the folder where the **Deploy to Bitrise.io** Step will look for the test results to export them. It should be set to the `$BITRISE_TEST_RESULT_DIR` Env Var.
1. Make sure you have a **Deploy to Bitrise.io** Step in your Workflow.

   If your tests generate attachments, make sure the Step is of version 2.19.x or newer. To link attachments by file name, use version 2.26.0 or newer.
