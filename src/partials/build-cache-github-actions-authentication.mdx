You have four options to authenticate the Bitrise Build Cache CLI on GitHub Actions. The best method depends on where the job runs: on Build Hub runners there is nothing to set up, and on GitHub-hosted runners we recommend OpenID Connect (OIDC).

<Tabs>
<TabItem value="build-hub" label="Build Hub runners" default>

On [Bitrise Build Hub](/bitrise-build-hub/build-hub-for-github-actions/build-hub-for-github-actions-overview) runners there is nothing to set up. The machine is already connected to your Bitrise Workspace, so the CLI picks up the credentials from it: you don't create a token, and you don't add any secret, variable or environment variable to your workflow.

The machine pool has to belong to the same Workspace as the Build Cache you want to use.

:::note[Minimum CLI version]

Automatic authentication on Build Hub runners needs Bitrise Build Cache CLI v3.10.0 or later. The install command on this page always fetches the latest release, so this only matters if you pin the CLI to an older version. An older CLI doesn't recognize the machine's credentials and stops with a missing token error.

:::

If the CLI can't reach Bitrise to get a token, it falls back to the other methods on this page. A job that also sets `BITRISE_BUILD_CACHE_AUTH_TOKEN` and `BITRISE_BUILD_CACHE_WORKSPACE_ID` keeps working, and those values take precedence over the machine's own credentials.

</TabItem>
<TabItem value="oidc" label="OpenID Connect (OIDC)">

On GitHub-hosted runners, we recommend OIDC. There is no token to create, store or rotate: Bitrise trusts the GitHub Actions runs of your repository through an [OIDC trust policy](/bitrise-platform/integrations/oidc-authentication/oidc-for-bitrise), and each job exchanges its GitHub OIDC token for a short-lived Bitrise token.

To use OIDC, you need the following:

- You are an owner of the Bitrise Workspace. Other members don't see this option.
- The repository is on github.com. GitHub Enterprise Server is not supported.
- Bitrise Build Cache CLI v3.15.0 or later. The install command on this page always fetches the latest release, so this only matters if you pin the CLI to an older version.

If any of these doesn't apply, use a Workspace API token instead.

Bitrise creates the trust policy for you when you add a new Build Cache connection:

1. On Bitrise, select **Build Cache** from the left navigation menu and click **New connection**.
1. Select **GitHub Actions** as the CI provider, then select your build tool.
1. At the authentication step, select **Use OpenID Connect (OIDC)**.
1. Connect to GitHub and select the repository that will use the Build Cache.

   Bitrise creates a trust policy for the repository, or offers the existing one if the repository already has it. The policy matches every GitHub Actions run of that repository and grants the **viewer** workspace role, the lowest role that can access the Build Cache.
1. Copy the `permissions` and `env` blocks from the next step into your GitHub Actions workflow:

   ```yaml
   jobs:
     build:
       permissions:
         id-token: write   # lets the job request a GitHub OIDC token
         contents: read    # checkout; setting permissions drops the defaults
       env:
         BITRISE_BUILD_CACHE_WORKSPACE_ID: "<your workspace slug>"
         BITRISE_BUILD_CACHE_OIDC_POLICY_ID: "<your trust policy ID>"
   ```

   Neither value is sensitive, so you don't need a GitHub secret. In the example workflow on this page, these two blocks replace the `env` block of the GitHub-hosted runner job.

You can find the policy later on the **Workspace settings** page, under **Security**, on the **OIDC trust policies** tab.

:::note[A token in the job takes precedence]

If the job also sets `BITRISE_BUILD_CACHE_AUTH_TOKEN`, the CLI uses that token and skips the OIDC exchange. Remove the token from the job when you switch to OIDC.

:::

</TabItem>
<TabItem value="workspace-api-token" label="Workspace API token">

If you can't use OIDC on GitHub-hosted runners, use a [workspace API token](/bitrise-platform/workspaces/workspace-api-token). It belongs to the workspace rather than to a person, so it keeps working when someone changes roles or leaves the company.

Give the token at least the **viewer** workspace role: that is the lowest role that can access the Build Cache.

The job needs two values: 

- The token. It is sensitive and belongs in a GitHub secret.
- Your [workspace slug](/bitrise-ci/api/identifying-workspaces-and-apps-with-their-slugs). It is not sensitive and can be a GitHub variable. You can add both to a single repository, or to your organization so that every repository can use them.

1. On GitHub, open the repository or the organization you want to add them to, and select **Settings**.
1. In the sidebar, under **Security**, select **Secrets and variables**, then **Actions**.
1. On the **Secrets** tab, click **New repository secret**, or **New organization secret** if you are in the organization settings.
1. Set the name to `BITRISE_BUILD_CACHE_AUTH_TOKEN` and paste the Workspace API token as the value, then click **Add secret**.

   An organization secret also asks which repositories are allowed to use it.
1. Switch to the **Variables** tab and click **New repository variable**, or **New organization variable**.
1. Set the name to `BITRISE_BUILD_CACHE_WORKSPACE_ID` and your Bitrise Workspace slug as the value, then click **Add variable**.

   You can find the slug on the **Workspace settings** page of your Bitrise Workspace, under **General settings**.
1. In your GitHub Actions workflow, pass both to the job as environment variables:

   ```yaml
   jobs:
     build:
       env:
         BITRISE_BUILD_CACHE_AUTH_TOKEN: ${{ secrets.BITRISE_BUILD_CACHE_AUTH_TOKEN }}
         BITRISE_BUILD_CACHE_WORKSPACE_ID: ${{ vars.BITRISE_BUILD_CACHE_WORKSPACE_ID }}
   ```

</TabItem>
<TabItem value="personal-access-token" label="Personal access token">

:::caution[A Personal Access Token inherits your roles]

A [Personal Access Token](/bitrise-platform/accounts/personal-access-tokens#creating-a-personal-access-token) has the same roles as the user who created it. Its access changes whenever that user's roles change, and it stops working when the user leaves the Workspace. For a shared CI configuration, use a Workspace API token instead.

:::
