### Run the activation as its own step

The CLI publishes its configuration through `$GITHUB_ENV`, which GitHub Actions applies to the **following** steps of the job. If you activate the Build Cache and run your build inside the same `run:` block, the build does not pick up the configuration.

Keep activation in a step of its own, before the step that runs the build.

### Workflows triggered by forks cannot use the Build Cache

When a workflow run is triggered from a fork, GitHub does not give the run access to secrets or OIDC tokens. The CLI cannot authenticate in those runs, so the activation step fails. Skip the activation step for fork runs. For example, you can use the `github.event.pull_request.head.repo.full_name` context to check if the run is from a fork:

```yaml
- name: Activate Bitrise Build Cache for Gradle
  if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
  run: /tmp/bin/bitrise-build-cache activate gradle --cache --cache-push
```

### Keep dependency caching separate from the Build Cache

`actions/cache` does **dependency caching**: it saves the packages your build downloads, such as the Gradle or CocoaPods caches, and restores them on the next run so they don't have to be fetched again. On Bitrise CI, the key-based caching Steps do the same job. For more information, see [Dependencies and caching overview](/bitrise-ci/dependencies-and-caching/dependencies-and-caching-overview).

That is a different job from the Bitrise Build Cache, which reuses the **outputs** of the build itself: compiled classes, compiled sources and task results. The two work well together, so keep caching your dependencies.

What you should not do is put build outputs into the dependency cache. If, for example, `actions/cache` restores Gradle's local build cache directory (`~/.gradle/caches/build-cache-1`), the restored local copy serves the results that the Bitrise Build Cache would have served, and your remote cache hit rate drops to near zero. Cache the dependency directories, not the build output directories.
